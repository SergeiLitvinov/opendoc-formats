# Контракты модели OpenDoc

Адаптер использует официальный `opendoc-model==0.16.0`, импорт `opendoc_model`.

Общий контракт `ObjectMapping` включает отдельные исходные/целевые вхождения,
заменяющее представление, непрозрачный `NativeObjectLocator`, полноту оценки
и состояния временного, опубликованного, отклонённого или утратившего актуальность
результата. Сериализация принадлежит модели. Вычисление соответствий, проверка
нативных адресов и отражение фактической транзакции принадлежат адаптеру и вызывающей
стороне; C-MAP-01 / OF15 остаются открытыми до такой приёмки.
Парсеры TeX/OOXML/PDF, внешние движки и способы чтения принадлежат OpenDoc Formats.
Модель остаётся самостоятельной MIT-библиотекой без обязательных движков.

## Доступные контракты

| Область | Контракт модели | Работа адаптера |
| --- | --- | --- |
| Поддержка и потери | `CapabilityProfile`, `FeatureCapability`, `PreservationRecord`, `PreservationState` | Объявлять конечный профиль и записывать semantic/opaque/visual/lost/rejected с причиной и местом; OF15 |
| Исходный синтаксис | `SourceFile`, `SourceSpan`, `SourceMap`, `UnknownFragment` | Связывать разобранные узлы с исходником, сохранять неизвестные фрагменты с лимитами; OF04/OF14 |
| Поля и диапазоны | `TextPosition`, `TextRange`, `Field`, `BibliographyEntry`, `Comment`, `Revision`, `ContentControl` | Разбирать и экспортировать реальные поля, цитаты, комментарии и revisions; OF05 |
| Вектор | `AffineTransform`, `PathCommand`, `Paint`, `VectorPath`, `VectorGroup`, `VectorScene` | Развивать graphics state и связи с integration scene; конечный ресурсный PDF writer реализован, полнота исходного PDF остаётся OF07 |
| Диаграммы и стили | `ChartSeries`, `ChartAxis`, `Chart`, `SceneStyle` | Разбирать данные, группы, theme/master/layout без выдачи картинки за редактируемые данные; OF06 |
| Специализированные данные | Типы reading order, annotation, form, media/timing, math AST и sheet/cell в `integration_types` | Заполнять поддержанную семантику форматов; не исполнять actions; OF04/OF06/OF07/OF08/OF13 |

`get_integration` / `set_integration` связывают типизированные данные с документом;
модель проверяет ссылки, лимиты и JSON. Адаптеру не следует вводить параллельную
схему для уже существующих типов. Наличие типа в модели не означает, что парсер
конкретного формата уже заполняет его: критерии реализации находятся в [TODO](todo.md).

## Требования к дальнейшему развитию

Изменение модели требуется только для подтверждённого пробела её публичного
контракта. Предложение должно содержать минимальный документ, ожидаемую семантику,
JSON roundtrip, ограничения и проверку обратной совместимости. Сначала адаптер
использует существующие integration contracts и проверяет их на реальном corpus.

«Полный парсинг» определяется конечным профилем спецификации. Неизвестные Office
extensions, динамический HTML и произвольные TeX-программы требуют сохранения
оригинала и честной диагностики; наличие модели не делает их безопасно исполняемыми.

## Предпочтительная ширина таблицы и ячейки

Модель предоставляет `WidthMeasure`, `get_preferred_width` и `set_preferred_width`
для таблицы/ячейки: absolute/relative/auto/unspecified, JSON roundtrip и
согласование с legacy `width_twips`. Подтверждённый случай — таблица 20×3,
общая ширина 9600 twips, ячейки `pct=500/4000/500`: проценты нельзя подменять
равными абсолютными ширинами. Два JSON roundtrip и Word проверяют исходные
48/384/48 pt и одну страницу.

Адаптер заполняет общий `WidthMeasure`, сохраняет исходный `docx_preferred_width`
для точной обратной записи и мигрирует прежние JSON при публичном импорте.
Явные правки и удаление типизированной ширины имеют приоритет; два цикла и правки
проверены по XML и в Word. Native OOXML type/value остаются обязанностью адаптера.

## Семантика подписи и заголовков таблицы

Модель предоставляет `TableSemantics`, `TableRowSemantics`, `TableCellSemantics`
и группы строк/колонок. Проверенный пример HTML содержит caption, th scope=col/row,
IDs/headers и два цикла JSON. Адаптер сохраняет их в стандартных блоках и
расширяемых properties; это временный форматный контракт, без дублирования модели.

Остаётся перенести проверенный форматный профиль на общие декларации,
сохранив миграцию прежних JSON и проверку caption ownership, header IDs и групп.
Нативные HTML-атрибуты и правила безопасного вывода остаются обязанностью адаптера.

## Оглавление и геометрия страниц

Модель предоставляет `Outline`, `OutlineEntry`, `OutlineTarget`, getters/setter
и явный remap ID. JSON сохраняет иерархию, назначения и неизвестные поля;
внешние URI инертны. Адаптер использует общий контракт, без своей схемы оглавления.
PDF заполняет общий outline и мигрирует прежние extensions при публичном JSON
импорте; конечный native writer сохраняет hierarchy, page points/zoom, URI и
body paragraph anchors. Полные actions/named destinations остаются в OF07;
исходная навигация EPUB — в OF08. PDF заполняет общий `PageGeometry` и нативно
восстанавливает media/crop/rotation с typed edits и удалением. Source coordinates:
x=PDF x, y=-PDF y, без смешения viewport с media dimensions. Legacy JSON без
исходных MediaBox сохраняет неизвестность, а не получает предполагаемые размеры.
Полные page boxes/UserUnit и скрытая структура остаются в OF07.

## Контракт поворота изображения

Требуется формально закрепить направление и центр `Box.rotation`, а также
различие исходной рамки и axis-aligned bbox. В конечном PDF writer-профиле
рамка без `pdf_image_transform` поворачивается по часовой стрелке вокруг центра;
нативная PDF matrix задаёт исходные оси, а box — её bbox до дополнительного поворота.
Проверены произвольный угол, отражение, shear и обрезка. Общая модель должна
описать этот смысл явно; параллельный тип геометрии в адаптере не вводится.

## C-FONT-01: ссылка стиля на программу шрифта

Model 0.14.0 реализует `FontReference`, `get_font_reference`, `set_font_reference`
и типизированный обход ссылок. Контракт закрыт на стороне модели: family остаётся
отдельной подписью; codec, validation, cascade, правка, удаление и композиция
принадлежат SDK. Разбор шрифтовых программ в модель не переносится.

Адаптер использует официальный контракт без своей схемы. Нативное PDF text device
предоставляет программу каждого нарисованного глифа; её полный SHA-256 сопоставляется
с сохранённым FONT-ресурсом. Проверяются Unicode и координаты каждого символа.
Совпадение имени, метрик или cmap не выбирает программу. Если API/свидетельство
недоступно либо соответствие неоднозначно, ссылка остаётся неизвестной;
конфликтующие программы нельзя молча подменить одной из них.

Word writer разрешает прямые и унаследованные ссылки через SDK, сохраняет исходную
модель и создаёт отдельное нативное имя/relationship для каждой программы.
Публичный DOCX reader восстанавливает ссылки из font-table slots; два JSON/DOCX
цикла сохраняют разные контуры глифов при одинаковом семействе. Проверены правка
ссылки, наследование и отказ при снятии необходимой привязки. Неподдерживаемый
индекс лица не становится нулём: конечный профиль встраивает standalone TTF/OTF.
Коллекции шрифтов, отсутствующие/непригодные программы и сложные случаи извлечения
остаются задачами адаптера в OF17. Байты и лицензионные уведомления программы
сохраняются; системная установка шрифтов не требуется.

Регрессия: `tests/writers/test_pdf_docx_complex.py::test_same_family_different_programs_keep_explicit_model_binding`.

## C-GRAPHICS-01: общая обрезка и композиция смешанной группы

Статус: часть Model закрыта официальным выпуском 0.15.0. Адаптер использует
`VectorClip`, `SceneOccurrence`, `GroupCompositing` и публичные scene setters.
Нативная приёмка адаптера остаётся отдельной: исходный текст сохраняется целиком,
typed clip/group правки и удаления не подменяются legacy данными. Прямоугольный
RGB-профиль компилирует композицию в векторные области; редактируемая обрезка
глифов в Word и произвольная смешанная композиция остаются в TODO.
Расширенные `VectorScene`, `VectorGroup`, `VectorClip` и `SceneOccurrence`
связывают нативные операции с якорями узлов. Новый параллельный scene graph
в Formats не вводится. Нативный `pdf_graphics` — ограниченное свидетельство
PDF-интерпретатора, а не общий контракт редактирования или JSON codec.

Минимальные независимые оригиналы создаёт `tests/writers/test_pdf_docx_graphics.py`:

- `grouped_form(opacity=.5)`: два пересекающихся прямоугольника внутри Form
  Transparency, второй с собственной alpha=.5, поверх цветного фона. Общая
  opacity=.5 применяется к результату композиции группы. Умножение прозрачности
  каждого ребёнка на .5 меняет цвет пересечения. `isolated`, `knockout`,
  blend mode и неизвестный режим не должны превращаться в Normal по умолчанию.
- `grouped_form(partial_text=True)`: область [80, 240, 25, 30] в исходных PDF
  координатах пересекает строку «Partially hidden text». Весь текст остаётся
  редактируемым в Model, но скрытые глифы не должны появляться в представлении.
- `curved_clip(even_odd=True)`: вложенные области с кубическими кривыми и
  отверстием; `image_form(repeated=True)` — разные обрезки одного ресурса.

Улучшение относительно Model 0.14.0: children/roots сцены дают общее владение
смешанной группой и paint occurrences; добавлены явные
isolation/knockout/blend и привязка общей области к тексту.
Официальный API развивает существующие типы:
типизированная область с winding rule/transform и однозначной системой координат,
привязка к конкретному вхождению узла/группе, параметры композиции и явный unknown.
Mask-ссылка остаётся ссылкой на ресурс, без исполнения программы.

Model владеет типами, проверкой ссылок, JSON roundtrip, remap, edit/remove и
лимитами количества команд, глубины, координат и циклов. Удалённая typed область
не восстанавливается из legacy properties. Старые документы читаются без
придуманной обрезки; неизвестный режим/отсутствующая ссылка диагностируются.
Formats владеет чтением PDF q/Q, cm, W/W*, Do, ExtGState, матрицами и ресурсными
scope, выбором представления SVG/DrawingML и сравнением с исходным PDF в Word.
PDF-операторы, PyMuPDF и правила Word в SDK не переносятся.

Приёмка: два JSON/форматных цикла, изменение/удаление clip и group opacity,
разные occurrences одного изображения, сохранение порядка детей и видимого
пересечения, отсутствие dangling references и ограниченный отказ на циклы/лимиты.
Вне подтверждённого конечного профиля Formats отклоняет эти сложные случаи
атомарно, сохраняя исходный PDF и прежнее назначение. Нейтральная группа Normal,
opacity=1, knockout=false и подтверждённая обрезка обслуживаются частным
проектором Formats без изменения общей модели.

## C-GRAPHICS-02: цветовое пространство композиции группы

Статус: закрыт официальным выпуском Model 0.16.0 и подключён адаптером.
`GroupColorSpace` и `GroupCompositing.color_space` задают пространство композиции;
`get_scope_color_space` / `set_scope_color_space` обслуживают чтение, правку и
удаление. Поддержаны rgb/gray/cmyk/srgb/icc, ссылка на ICC-ресурс и явный unknown.
SDK проверяет ссылки, remap, лимиты и JSON; цветовое преобразование принадлежит
Formats. Улучшение относительно 0.15.0: пространство промежуточной композиции
больше не приходится хранить только форматным свидетельством в `extra`.

Минимальный оригинал: `grouped_form(opacity=.5)` из
`tests/writers/test_pdf_docx_graphics.py`: красный прямоугольник, синий alpha=.5,
общая opacity=.5 поверх RGB фона (.9,.85,.6). Замена только `/Group/CS` с
`/DeviceRGB` на `/DeviceGray` меняет измеренный MuPDF RGB в пересечении
с (179,109,139) на (165,158,126), при неизменных остальных параметрах и Paint.
В Formats нативное значение в `VectorGroup.extra` служит только свидетельством.
Экспорт читает официальную декларацию; её удаление, unknown, непроверенный профиль
или не-RGB композиция вызывают отказ, даже если старое свидетельство содержит RGB.
PDF device явно объявляет RGB-профиль интерпретации; разрешение нативного
наследования выполняет адаптер. Старое свидетельство без такой декларации не
получает предполагаемый RGB по цвету дочерних объектов.

Старый документ не получает предполагаемое пространство; неизвестное
расширение сохраняется. PDF имена `/CS`, DefaultRGB, OP/OPM и преобразования
цвета остаются в адаптере; SDK не импортирует renderer или ICC движок.

Проверка адаптера: `tests/writers/test_pdf_group_color_space.py` — два JSON-цикла,
правка/удаление, unknown, Gray/CMYK и прежний scene без декларации. Отказ атомарен,
native extra не восстанавливает удалённые данные. Независимые PDF, цвета
пересечения и отсутствие растеризации относятся к приёмке Formats. Формальная
декларация не объявляет поддержку нативного цветового преобразования.

## C-LIST-02: границы и продолжение пункта списка

Статус: агент Model подтвердил пробел и реализует общую связь; официальный
выпуск и подключение адаптера остаются открытыми. Рассматриваются ссылки через
существующие якоря на первый абзац того же пункта и на родительский пункт.
Официальный Model 0.16.0 уже содержит `ListItem`, `get_list_item`, `set_list_item`
и `iter_list_numbers`; новый параллельный список в Formats не нужен.
`ListItem` задаёт принадлежность абзаца к группе/уровню и start/restart. Каждое
вхождение ordered item увеличивает счётчик; plain paragraph не задаёт, находится
он внутри того же пункта или уже вне списка. Родитель пункта не объявлен.

Минимальные независимые оригиналы, воспроизводимые в `tests/readers/test_tex_lists.py`:

```tex
\begin{enumerate}
\item First.

Continuation of the same item.
\end{enumerate}
Outside.
```

Три абзаца: первый имеет номер 1, второй принадлежит тому же пункту без нового
номера, третий находится вне списка. `ListItem` на втором абзаце создаёт номер 2;
отсутствие роли делает его неотличимым от третьего. Также нужен случай пустого
родительского пункта, содержащего только вложенный список. Исходные TeX байты
удерживают различие, но не заменяют общий редактируемый контракт.

Просьба сначала проверить применимость существующих типов, traversal и операций.
Если пробел подтверждён, расширить существующую семантику идентичностью пункта,
связью продолжения и, при необходимости, родительской принадлежностью. Не
предписывается отдельный AST: способ расширения выбирает Model. Пункт может
содержать несколько абзацев и дочерний список; plain outside paragraph остаётся
свободным. Числовое значение вычисляется на пункт, не на каждый его абзац.

Приёмка Model: два JSON-цикла; стабильные ссылки при remap/merge/extract;
правка/удаление связи без возврата legacy properties; явная диагностика dangling
и циклических связей; выбранные лимиты. Старый `ListItem` и нумерация остаются
совместимыми; неизвестная принадлежность не угадывается из соседнего абзаца.
Особо проверить удаление первого абзаца пункта с сохранённым продолжением и
пустого родителя дочернего списка; точное правило должно быть документировано.

Formats владеет TeX itemize/enumerate/item, optional labels, DOM/OOXML-маркерами,
native group IDs, стилем нумерации, парсингом, writer и сравнением исходника с
результатом. Custom labels могут оставаться явным unsupported профилем Formats;
их строки и TeX-команды в SDK не переносятся. Model владеет только общей ролью,
ссылками, codec, validation, remap и бюджетами. До согласования Formats сохраняет
полный исходник и located opaque records; замена продолжения новым `item`
не принимается как нативный экспорт без потерь структуры.
