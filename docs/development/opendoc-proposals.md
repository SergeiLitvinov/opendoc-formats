# Контракты модели OpenDoc

Адаптер использует официальный `opendoc-model==0.6.0`, импорт `opendoc_model`.
Парсеры TeX/OOXML/PDF, внешние движки и способы чтения принадлежат OpenDoc Formats.
Модель остаётся самостоятельной MIT-библиотекой без обязательных движков.

## Доступные контракты

| Область | Контракт модели | Работа адаптера |
| --- | --- | --- |
| Поддержка и потери | `CapabilityProfile`, `FeatureCapability`, `PreservationRecord`, `PreservationState` | Объявлять конечный профиль и записывать semantic/opaque/visual/lost/rejected с причиной и местом; OF15 |
| Исходный синтаксис | `SourceFile`, `SourceSpan`, `SourceMap`, `UnknownFragment` | Связывать разобранные узлы с исходником, сохранять неизвестные фрагменты с лимитами; OF04/OF14 |
| Поля и диапазоны | `TextPosition`, `TextRange`, `Field`, `BibliographyEntry`, `Comment`, `Revision`, `ContentControl` | Разбирать и экспортировать реальные поля, цитаты, комментарии и revisions; OF05 |
| Вектор | `AffineTransform`, `PathCommand`, `Paint`, `VectorPath`, `VectorGroup`, `VectorScene` | Развивать graphics state и связи с integration scene; конечный ресурсный PDF writer реализован, полнота исходного PDF остаётся OF07 |
| Диаграммы и стили | `ChartSeries`, `ChartAxis`, `Chart`, `SceneStyle` | Разбирать данные, группы, theme/master/layout без выдачи картинки за редактируемые данные; OF06 |
| Специализированные данные | Типы reading order, annotation, form, media/timing, math AST и sheet/cell в `integration_types` | Заполнять поддержанную семантику форматов; не исполнять actions; OF04/OF06/OF07/OF08/OF13 |

`get_integration` / `set_integration` связывают типизированные данные с документом;
модель проверяет ссылки, лимиты и JSON. Адаптеру не следует вводить параллельную
схему для уже существующих типов. Наличие типа в модели не означает, что парсер
конкретного формата уже заполняет его: критерии реализации находятся в [TODO](todo.md).

## Требования к дальнейшему развитию

Изменение модели требуется только для подтверждённого пробела её публичного
контракта. Предложение должно содержать минимальный документ, ожидаемую семантику,
JSON roundtrip, ограничения и проверку обратной совместимости. Сначала адаптер
использует существующие integration contracts и проверяет их на реальном corpus.

«Полный парсинг» определяется конечным профилем спецификации. Неизвестные Office
extensions, динамический HTML и произвольные TeX-программы требуют сохранения
оригинала и честной диагностики; наличие модели не делает их безопасно исполняемыми.

## Предпочтительная ширина таблицы и ячейки

Модель предоставляет `WidthMeasure`, `get_preferred_width` и `set_preferred_width`
для таблицы/ячейки: absolute/relative/auto/unspecified, JSON roundtrip и
согласование с legacy `width_twips`. Подтверждённый случай — таблица 20×3,
общая ширина 9600 twips, ячейки `pct=500/4000/500`: проценты нельзя подменять
равными абсолютными ширинами. Два JSON roundtrip и Word проверяют исходные
48/384/48 pt и одну страницу.

Адаптер сохраняет исходный `docx_preferred_width` в расширяемом property bag.
Остаётся заполнить согласованный типизированный контракт в адаптере и проверить
обратную запись, явные правки и совместимость старых JSON. Native OOXML type/value
и их миграция остаются обязанностью адаптера; самостоятельная модель ширины не нужна.

## Семантика подписи и заголовков таблицы

Модель предоставляет `TableSemantics`, `TableRowSemantics`, `TableCellSemantics`
и группы строк/колонок. Проверенный пример HTML содержит caption, th scope=col/row,
IDs/headers и два цикла JSON. Адаптер сохраняет их в стандартных блоках и
расширяемых properties; это временный форматный контракт, без дублирования модели.

Остаётся перенести проверенный форматный профиль на общие декларации,
сохранив миграцию прежних JSON и проверку caption ownership, header IDs и групп.
Нативные HTML-атрибуты и правила безопасного вывода остаются обязанностью адаптера.
