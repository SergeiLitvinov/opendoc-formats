# C-DOCX-FLOW-01: потоковый Word из PDF-модели

Статус: предложение публичного контракта, API ещё не реализован. Владелец —
OpenDoc Formats. Общие типы документа, FONT references и JSON остаются в Model;
изменений Model для описанного профиля не требуется.

## Подтверждённая граница

Собственная таблица 3×3 после выбора двух строк и двух столбцов содержит
редактируемые ячейки 2×2 и изменённый `Table.box`. Отдельные восемь векторных
линий исходной сетки остаются в модели. Нативные `pdf_column_edges` и
`pdf_row_edges` описывают исходные четыре границы каждой оси, поэтому не могут
автоматически считаться сеткой отредактированной таблицы.

Публичный `write_docx_model` сохраняет строгий позиционированный профиль:
изолированные линии с нулевой площадью дают `pdf-docx.layout`. Снятие `Table.box`
даёт `PDF table geometry remains unknown`, а не выбор потокового экспорта.
Оба отказа воспроизведены с сохранением исходной модели и прежнего назначения.
Ограничение нельзя обходить изменением `source_format`, очисткой provenance,
приватных свойств либо молчаливым удалением векторных ресурсов.

## Предлагаемый интерфейс

Явный форматный профиль должен выбираться и в `write_document`, и в прямом
`write_docx_model`. Возможная форма — `DocxProfile(layout="flow")` через
`ExportOptions.docx_profile` и keyword-only `profile` прямого writer. Эти имена
предложены для согласования и пока не являются доступным API.

Отсутствие профиля сохраняет строгую проверку позиционированного PDF → DOCX.
Потоковый профиль работает с частной копией и текущим порядком публичных blocks,
rows и cells. Таблица остаётся нативной Word-таблицей; сохраняются текст, merges,
стили и ссылки. Отсутствующий `Table.box` допустим именно в явном flow-профиле.
Сетка вычисляется по текущим ячейкам и общим объявлениям ширины; исходные PDF
edges не восстанавливают удалённые строки или столбцы.

Потеря исходных координат/пагинации должна иметь явную LOSS с source locations;
политика качества вправе отклонить такой экспорт. Это не заявление о сохранении
оригинального отображения. FONT bindings и отсутствующие глифы проверяются
обычным preflight без подмены явно связанной программы системным шрифтом.

## Векторные данные

Неподдержанная графика по умолчанию вызывает отказ. Распознанные линии сетки
можно заменить нативными границами Word-таблицы только после доказанной связи
с ячейками и проверки stroke/color/dash/caps. Карта source → native replacement
должна явно учитывать каждый occurrence, включая линии удалённой части сетки.
Неоднозначность не должна объявляться успешной дедупликацией.

Несопоставленные линии требуют отдельного принятого нативного Word line profile
либо явного отказа. SVG нулевой площади и растеризация без разрешённой политики
не являются приёмкой редактируемого вектора. Исходные ресурсы и provenance
сохраняются в каноническом документе; сохранённое вложение не заменяет отчёт
о видимом содержимом результата.

## Приёмка

- Собственный PDF с таблицей 3×3, внешним абзацем и второй страницей: выбрать
  2×2, поменять порядок blocks, пройти JSON и экспорт с явным flow-профилем.
- В DOCX присутствуют ровно выбранные редактируемые ячейки и заявленный порядок;
  два цикла и нативная правка не восстанавливают удалённые строки/столбцы.
- Каждый векторный occurrence имеет подтверждённое представление/замену или
  отказ с location; исходная сетка не рисуется поверх обрезанной таблицы молча.
- Сравнить принятые границы и линии с независимым исходным рендером; semantic
  reflow не выдавать за позиционную приёмку. Проверить merges и неравные ширины.
- Неизменность входного JSON, FONT references и resources; пределы, отмена,
  атомарное назначение и отказ quality gate сохраняют прежний файл.

Реализация flow-профиля и конечного grid/line mapping остаётся открытой задачей.
