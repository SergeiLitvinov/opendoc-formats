# C-DOCX-FLOW-01: потоковый Word из PDF-модели

Статус: реализован конечный профиль `pdf-semantic-flow-v1`. Владелец — OpenDoc
Formats. Общие типы документа, FONT references, JSON и валидация принадлежат
`opendoc-model==0.19.0` (импорт `opendoc_model`); новых типов или codec в Formats нет.

## Публичный интерфейс

```python
from opendoc_formats import DocxProfile, ExportOptions, write_document
from opendoc_formats.writers.docx_writer import write_docx_model

profile = DocxProfile(layout="flow")
report = write_docx_model(model, "result.docx", profile=profile)
# Тот же профиль через реестр:
report = write_document(model, "result.docx", options=ExportOptions(docx_profile=profile))
```

По умолчанию используется `layout="preserve"`: строгая позиционированная проверка
PDF → DOCX сохраняется. `flow` принимает каноническую PDF-модель, работает с
частной копией и текущим порядком blocks, rows и cells. Уже подготовленный
позиционированный Word view не является каноническим входом. `Table.box` может
присутствовать или отсутствовать. Координаты Paragraph/Table удаляются только
в копии; изображения сохраняют размеры и становятся inline.

Экспорт выдаёт LOSS `docx.flow-layout`: исходные координаты и пагинация
не сохраняются. Это редактируемая семантическая компоновка, без заявления о
совпадении страниц исходного PDF. `quality_gate` вправе отклонить LOSS, например
через `quality_gate=lambda report, path: report.lossless`.

FONT bindings, программы и глифы проверяются обычным preflight. Адреса diagnostics,
включая подстановку Courier, относятся к исходным индексам модели до исключения
абзацев сетки. Неизвестный paint-state, скрытый, stroked или полупрозрачный
PDF-текст вызывают отказ. Другие потери содержимого также отклоняют публикацию;
предупреждения не скрываются.

## Редактируемые таблицы и учёт вектора

Принята обрезка собственной таблицы 3×3 до выбранных 2×2, изменение порядка
blocks и заголовка. Сохраняются ровно выбранные редактируемые ячейки и текст.
Исходные `pdf_column_edges`/`pdf_row_edges` описывают источник и не восстанавливают
удалённые строки. Ячейки должны образовывать непрерывный прямоугольник исходной
сетки; каждая имеет `pdf_cell_bbox`, ширины столбца согласованы.
Общие явные ширины сохраняются; при их отсутствии используются ширины выбранных
ячеек, а не число исходных edges.

Исходные горизонтальные/вертикальные объединения принимаются для полной
измеренной таблицы: spans должны совпадать с bbox и размещением в исходной сетке.
Границы строятся объединением сторон ячеек, поэтому внутри merged cells не
появляются лишние линии. Физические grid widths задаются отдельно; ширина
объединённой ячейки равна сумме её столбцов. Перед публикацией фактические
`w:gridSpan` и `w:vMerge` сверяются с планом, включая continuation cells.
Для такой таблицы native locator карты указывает на весь `w:tbl`, а
`cell_topology` фиксирует проверенные строки/столбцы/spans; это по-прежнему
карта grid occurrences, не полный C-MAP-01.
[Приёмка объединений](docx-flow-merges-evidence.json).
Для собственного корпуса Word 16.0 build 16.0.17932 подтвердил семь логических
ячеек, ширины 100/200 pt и редактирование вертикального объединения. Выданные
Word PDF для результата и двух циклов совпадают по пикселям в MuPDF и Poppler
при 108 dpi; сохранённая Word-правка повторно импортируется с `row_span=2`.

При импорте измеренной merged-таблицы Formats сохраняет `pdf_source_cell_bounds`
в свойствах таблицы: исходные bbox всех логических ячеек, в тех же pt, что и
`pdf_cell_bbox`. JSON сохраняет снимок отдельно от редактируемых rows/cells.
Flow сверяет полный исходный прямоугольник без перекрытий и дыр, сохраняет
каждую исходную линию в карте и принимает прямоугольную обрезку по целым ячейкам.
Сохраняются оставшиеся spans и ширины; линии вне выбранных границ учитываются
как исключённые. При отсутствии снимка merged crop явно отклоняется; догадка по
оставшимся ячейкам не восстанавливает потерянную исходную topology.
Объём исходной сетки ограничен `DocumentLimits.max_nodes`, обход проверяет отмену.
[Приёмка обрезки](docx-flow-merge-crop-evidence.json).

### Идентичность сетки после правки Word

Для однострочного crop Word при нативной правке может свернуть избыточный столбец:
две ячейки и ширины 200/100 pt остаются, но физическая сетка 100/100/100 pt
становится 200/100 pt. Без source binding исходный `column_span=2` не выводится
из ширины или текста.

Однострочный flow с минимум двумя логическими ячейками и горизонтальным merge
получает явный snapshot исходных grid widths/spans. Formats сохраняет его в
собственном custom XML, связанном стандартной OPC customXml relationship,
и привязывает к таблице скрытой Word-закладкой `_og_<id>`. Структура `w:tbl`,
строки и ячейки остаются обычными: content controls, wrappers и растеризация
не используются. Word вправе менять имена частей и числовой bookmark ID;
связь разрешается по OPC relationship и уникальному имени закладки.

При импорте должны совпасть ровно одна привязка, её начало/конец в той же таблице,
один snapshot версии 1, число логических ячеек и все их границы относительно
исходной сетки. Только тогда исходные widths/spans возвращаются в Model.
Текст не участвует в идентификации; изменение текста и его форматирования
не отменяет связь. Ширины служат проверкой явного snapshot, а не основанием
для угадывания отсутствующих столбцов. После нативной замены текста Word
действительно записывает два столбца, а Model восстанавливает три и span 2.
Ещё два JSON/DOCX-цикла сохраняют результат без накопления копий snapshot.

Изменение границ, удаление ячейки, повреждение/дублирование привязки, неизвестная
версия или неоднозначная связь сохраняют фактическую сетку Word. Непроверенная
identity отмечается located WARNING `docx.source-grid`; старые ячейки не создаются.
При удалении самой привязки snapshot остаётся нативным opaque evidence.
Формат snapshot ограничен 64 KiB, 256 grid columns/cells и положительными int32
widths; поиск custom XML ограничен 1 MiB, внешние relationships не загружаются,
сущности и DTD не разрешаются. До публикации проверяются записанные snapshot,
OPC-связь и bookmark pair; подмена даёт атомарный отказ.

Formats владеет этой нативной metadata. `docx_source_grid_identity` в свойствах
таблицы содержит `id`, `grid`, `spans`, `state` и исходные part bindings для
восстановления OPC graph; общие Model DTO/кодеки не расширены. Это локальная
проверяемая связь, не цифровая подпись или универсальная cell identity при
произвольной структурной правке. Многострочные случаи и изменённая геометрия
остаются в TODO. [Проверки, наблюдения Word и hashes](docx-source-grid-evidence.json).

Конечный профиль заменяет полный набор отдельных горизонтальных/вертикальных
линий исходной сетки на нативные границы Word-таблицы и её ячеек. Требуются однозначная
связь, непрозрачные SRGB stroke, обычный blend, отсутствие fill,
clip/dash и butt caps. Допустимы ширины 0,25; 0,5; 0,75; 1; 1,5; 2,25; 3; 4,5; 6 pt
из [нативного набора Word](https://learn.microsoft.com/en-us/office/vba/api/word.wdlinewidth).
Конфликт правки границ с исходной сеткой вызывает отказ. SVG, raster fallback
и молчаливое удаление линий не используются.

Внешние стороны и внутренние горизонтальные/вертикальные линии могут иметь
разные цвета и толщины. Если каждой из шести ролей соответствует один стиль,
они записываются в `w:tblBorders`. После обрезки исходная внутренняя линия
получает роль новой внешней стороны с сохранением своего стиля.

Если общего стиля роли недостаточно, строится поклеточный план по исходным
`pdf_cell_bbox`. Каждая полная логическая сторона должна иметь один стиль;
общие линии соседних ячеек получают одинаковые декларации. В таблице явно
отключаются шесть общих границ, каждая физическая ячейка получает четыре
`w:tcBorders`. Для `vMerge` верхняя/нижняя сторона проецируется только на начало/
конец объединения; внутри него записывается `none`, а боковые линии сохраняются.
Поддержаны исходные горизонтальные/вертикальные spans и прямоугольные crops.
Смена цвета/толщины внутри одной логической стороны пока отклоняется, а не
сводится к одному усреднённому штриху. Ручная декларация границ, противоречащая
измеренному источнику, требует явного согласования.

До публикации фактические роли, цвет, размер, отсутствие дополнительных
атрибутов, физические ячейки и merge topology проверяются по записанному OOXML.
Подмена `tcBorders` или линии внутри continuation вызывает атомарный отказ.
Дополнительный план ограничен 1000000 сравнений отрезков со сторонами;
обход проверяет отмену и не изменяет исходную Model. `cell_borders` и
`cell_topology` в mapping target фиксируют физический план, locator указывает
на весь `w:tbl`. Расширение общих DTO/кодеков Model не понадобилось.

Реальный Word подтвердил ширины, цвета и толщины всех сторон двух собственных
таблиц: cropped 2×2 с разными границами каждой ячейки и таблицы с обоими типами
объединений. Шесть Word PDF после двух JSON/DOCX-циклов совпали внутри MuPDF
и Poppler при 108 dpi. Нативная правка текста сохранила границы и spans.
Это приёмка данных случаев в flow-компоновке; совпадение страниц исходного PDF
не заявляется. [Доказательства и границы](docx-flow-cell-borders-evidence.json).

Каждая исходная граница может состоять из нескольких collinear отрезков.
Их интервалы должны полностью покрывать границу без пробелов и перекрытий
в пределах прежнего допуска координат 0,0001 pt. Сумма абсолютных отклонений
всех стыков и двух концов ограничена этим допуском на всю границу: множество
малых пробелов/наложений не может накапливать большую ошибку.
[Проверки суммарного допуска](docx-flow-tolerance-evidence.json).
Стиль у всех отрезков одинаков;
полные дубликаты, неоднозначный владелец, нулевая длина и выход за границу отвергаются.
Обход расходует общий бюджет сопоставлений и проверяет отмену при проверке покрытия.
Каждый отрезок остаётся отдельным source occurrence. При обрезке ячеек видимость
определяется пересечением отрезка с выбранной границей, а не только координатой
его оси. Поэтому полностью исключённые отрезки не получают ложной связи с Word.
Проверены совпадение исходных PDF-пикселей, одинаковый XML Word-таблиц для цельной
и составной сетки, JSON/DOCX-цикл и атомарные отказы. В Microsoft Word 16.0,
build 16.0.17932 принят crop 2×2: текст, ширины по 100 pt, чёрные границы 1 pt,
outline level 2, два цикла и отдельная нативная правка. Шесть выданных Word PDF
для цельной/составной сетки и циклов имеют одинаковые пиксели в MuPDF и Poppler
при 108 dpi. Это приёмка собственного конечного корпуса, не доказательство
пиксельного равенства Word исходному PDF или всех вариантов составных сеток.
[Свидетельство составной сетки](docx-flow-fragments-evidence.json).

`report.metrics["object_mapping"]` использует общие типы Model: каждый occurrence
сетки записан как source с provenance. Видимые линии сопоставлены проверенному
`word/document.xml#/w:document/w:body/w:tbl[…]/w:tblPr/w:tblBorders`; исключённые
линии за пределами выбранного диапазона отмечены LOST с причиной. В карте есть
SHA256 фактического результата и статус публикации. Область карты — только
объявленные grid occurrences; это не полный инвентарь документа и не lossless.

Несопоставленные/повторные линии, неоднозначная принадлежность, неполная сетка,
объединённые ячейки сетки, нестандартный stroke, вложенный вектор, graphics groups,
неподдержанные interactions и opaque/lost записи дают расположенный отказ.
Развитие профиля остаётся в [TODO](todo.md#сокращение-pdf-движков-of17-p1).

## Лимиты, отмена и зависимости

Сохраняются выбранные `DocumentLimits`. На оси допускаются 2–256 edges,
сопоставление ограничено 1 000 000 сравнений и проверяет отмену внутри циклов.
Прямой writer выбрасывает `OperationCancelledError`; реестр возвращает
`export.cancelled`. Ошибка, отмена, лимит и отказ quality gate сохраняют прежний
файл. Исходная модель, FONT references, resources и provenance не меняются.
После успешного прямого commit поздний сигнал не выдаётся за rollback.

JSON → Word flow использует профиль `docx` (python-docx и lxml); принятые полные
TTF/OTF programs проверяются собственным кодом, а `fonts` нужен для настоящего
subsetting и неподдержанных metadata-профилей. PyMuPDF/pdf2docx/OpenCV/Pillow не нужны
самому flow-экспорту канонической JSON-модели. Для первоначального импорта PDF
по-прежнему нужен выбранный PDF-движок; его лицензия описана отдельно.

## Приёмка

`tests/writers/test_docx_flow.py` проверяет публичный и прямой API, crop 2×2,
перестановку blocks, два DOCX/JSON цикла, нативные границы и карту occurrences.
Проверены исходные адреса diagnostics, неизменность JSON, явные отказы,
непрозрачность текста, лимиты, отмена и атомарное назначение.

`tools/docx_flow_word_acceptance.ps1` проверяет собственные результаты в
Microsoft Word 16.0, build 16.0.17932: таблица 2×2, выбранный текст, ширины четырёх
ячеек по 100 pt, чёрная граница 1 pt и outline level 2. Word открывает исходный
flow и два цикла read-only с неизменными хешами, выдаёт по две страницы и сохраняет
отдельную нативную правку ячейки. PDF, выданные Word для трёх файлов, имеют
одинаковые пиксели при 108 dpi; страницы также проверены независимым Poppler.
Эта приёмка относится к flow-результатам, не к пиксельному равенству исходному PDF.
