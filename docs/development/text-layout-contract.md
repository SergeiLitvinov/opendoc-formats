# C-TEXT-LAYOUT-01: позиции глифов и семантический текст

Статус: в рабочей сессии OpenDoc Model есть локальная реализация; потребительская
приёмка и подключение Formats не реализованы. Официальный Model 0.18.1 этих API
не содержит; исходники с новыми API не подменяют закреплённый release wheel.
Зависимая задача — C-PDF-01 в [TODO](todo.md).

## Доказанный пробел

В официальном Model 0.18.1 `TextRun` хранит текст и стиль, `TextRange` связывает
позиции по ID и offset, `FontReference` указывает программу шрифта. Общего
типизированного представления расположенных глифов и их связи с семантическими
диапазонами нет. `VectorPath` сохраняет контуры, но не заменяет редактируемый текст.
Произвольный JSON в properties сохраняет bytes данных, однако не даёт общего
контракта диапазонов, проверки актуальности или переноса ссылок при редактировании.

Formats уже получает `PdfTextSpan` / `PdfGlyphInfo` через
`PdfDocument.page_text_spans`. Прямые wire originals и отрицательные контроли —
`tests/native/test_pdf_text_spans.py` и `tests/readers/test_pdf_paint_matching.py`.
У одного текста могут быть отдельные fill/stroke occurrences; ligature continuation
содержит Unicode при glyph id `-1`. Нативный порядок не доказывает порядок чтения.
Полное отображение этих наблюдений в общую модель пока не принимается.

## Запрашиваемое поведение Model

Нужен необязательный форматонезависимый контракт text layout, использующий
существующие ID, диапазоны, единицы/преобразования, FONT resources и provenance.
Точные имена API и место хранения выбирает Model; новая параллельная модель
текста и форматный PDF codec не требуются.

- Layout связывает один или несколько логических диапазонов с размещёнными
  глифами/кластерами. Сохраняются позиции и преобразование в явно определённой
  системе координат, принадлежность странице/сцене и порядок в layout occurrence.
  Координаты конечны; порядок glyph records не становится порядком чтения.
- Связь many-to-many: `fi` может занимать два Unicode codepoints и один glyph,
  а один символ — несколько глифов. Отдельные paint occurrences сохраняются
  раздельно; от них нельзя требовать единственной общей привязки.
- Glyph id имеет смысл только относительно явной программы шрифта и face.
  Отсутствующий glyph/font/mapping остаётся явно неизвестным. Нативный sentinel
  `-1` не превращается в валидный glyph id; raw PDF observation остаётся у Formats.
  Нельзя выводить Unicode, glyph id, coverage или шрифт из соседства/имени семейства.
- Семантическая связь различает подтверждённую, неизвестную и утратившую
  актуальность привязку. Изменение текста не оставляет прежний layout молча
  действующим. Нужен документированный механизм проверки текста-владельца и
  явного remap либо invalidation после split/merge/extract/delete/ID remap.
  Повторная раскладка и восстановление актуальности принадлежат потребителю.
- Публичный codec сохраняет данные и неизвестные поля через два JSON-цикла,
  возвращает независимые контейнеры. Проверяются ссылки на диапазоны/страницу/
  сцену, тип и наличие FONT resource, границы offsets и выбранные бюджеты.
  Неподтверждённые связи не объявляются валидными из-за совпадения ID.
- Layout отсутствует у прежних документов без изменения их поведения.
  Недопустимые ссылки, NaN/Infinity, неверные индексы и квоты дают адресные ошибки;
  отказ не изменяет документ и не оставляет частично записанный layout.

Хранение должно быть ограниченным и пригодным для больших страниц. Не следует
неявно повышать общий бюджет или обходить nodes/depth/bytes/embedded bytes.
Model выбирает компактное типизированное либо ресурсное представление; его
публичные ограничения и расход квот должны быть документированы. Formats не
создаёт собственный общий JSON codec или неконтролируемый dict на каждый glyph.

## Разделение ответственности

| Model | Formats |
| --- | --- |
| Общие данные layout, диапазоны и FONT references | PDF parsing, извлечение glyph observations и font-program binding |
| Codec, независимые значения, лимиты и ссылочная валидация | Координатная проекция исходного формата и соответствие конкретного glyph семантике |
| Remap/invalidation и явная актуальность привязки | Shaping, измерения, clipping, paint seq/type/opacity, blend, layers и порядок рисования |
| Совместимость документов без layout | Writer, opaque/visual fallback, диагностика потерь и нативная приёмка |

Ни PyMuPDF, ни parser шрифта, ни layout/shaping engine не становятся обязательными
зависимостями Model. Model не определяет видимость PDF-текста, не исполняет
ресурсы и не гарантирует совпадение рендера. Formats не принимает сохранённую
геометрию за доказательство отсутствия потерь после редактирования.

## Приёмка

1. Обычный текст, `fi` 2:1, combining mark 1:N, RTL/непоследовательные позиции,
   два paint occurrences, неизвестное сопоставление и отсутствующий font binding.
   Эти случаи не обязаны быть получены из PDF: Model проверяет общие данные.
2. Два JSON-цикла, unknown fields и независимость вложенных значений;
   прежний документ без layout сохраняет своё представление.
3. Изменение текста, split/merge/delete/extract/remap: точные связи обновляются
   либо явно утрачивают актуальность, без молчаливого повторного использования.
4. Неверный FONT kind/face, dangling range/page/scene, offset вне текста,
   нечисловые/неконечные координаты и неверная размерность дают адресный отказ.
   Проверка face не подразумевает парсинг opaque шрифта: невозможность проверить
   реальный состав программы остаётся явной границей.
5. Квоты на границе, превышение и увеличенный пользовательский бюджет;
   отсутствие частичных записей и новых обязательных зависимостей.

Formats подключает только принятый публичный API. Отдельная приёмка PDF → Model →
JSON → PDF/DOCX должна сравнить исходную структуру и рендер независимого оригинала,
проверить правку и отчёт о неизвестных объектах. Закрытие этого контракта в Model
само по себе не закрывает C-PDF-01 или замену pdf2docx.
