# Архитектура и зависимость

OpenDoc Formats — самостоятельный **проект и пакет**, но **не автономная библиотека данных**.
Обязательная зависимость — OpenDoc Model 0.12.0: модель, ресурсы, единицы, диагностика,
JSON-кодек и валидация используются из официального выпуска без изменения его исходников.

OpenDoc Model 0.12.0 делает историю `Provenance.transformed` независимой от
изменяемых событий исходной истории. Схема JSON сохраняет совместимость.
Координаты, provenance и текстовые интервалы можно сохранять через JSON, однако
их сохранность сама по себе не доказывает визуальную точность нативного документа.
Общий inventory округляет геометрию; `compare_documents` не заменяет точное
сравнение всех integration-полей и проверку отображения. Расчёт компоновки и
извлечение координат из исходного формата остаются задачами адаптера.

```text
файл → реестр импорта → обработчик → DocumentModel OpenDoc
                                      ↓ валидация
файл ← атомарная публикация ← проверка ← реестр экспорта
```

## Границы проекта

Исходники, lockfile, CI, документация и версии управляются здесь.
Нет путей к соседним checkout, собственных копий `DocumentModel`, приложения, сервера,
очередей и задач. Публичное API — `opendoc_formats`, реестры `api` / `export`, нативные модули
`docx`, `pdf`, `office` и `package_resources`.
Текстовые структуры в `types.py` — проекция извлечённого текста для низкоуровневых движков,
а не альтернативная богатая модель документа.

В экосистеме okidoki OpenDoc задаёт общий контракт, Formats реализует переход между файловыми
форматами и этим контрактом. Приложения подключают пакет как обычную Python-зависимость.
Изменение приложения не требует изменения библиотеки; изменение контракта OpenDoc может
потребовать отдельного обновления и приёмки Formats.

## Полная автономность

Удаление зависимости потребовало бы собственного контракта модели, сериализации, ресурсов,
диагностики и валидации, затем отдельного моста к OpenDoc. Такое изменение затронуло бы
обработчики и публичное API. Для текущего выпуска принят общий контракт OpenDoc.

## Типы и стабильность

Все сигнатуры парсеров имеют аннотации. Модель и примитивы аннотированы конкретно;
`Any` остаётся на динамических границах необязательных движков, XML-интерфейсов
и неоднородных расширений metadata. Это постепенная типизация, а не обещание строгой
статической проверки каждого внутреннего пути. `uv run mypy` строго проверяет API,
экспорт, нативный доступ и структуры извлечения текста; `tools.audit` проверяет аннотации всех сигнатур.

`py.typed` поставляется в wheel. При версии 0.x публичные изменения контракта требуют minor-выпуска,
исправления совместимого поведения — patch. Низкоуровневые модули не имеют отдельного обещания
стабильности; для интеграции предпочтительны реестры и нативные API.

## Бюджет публичного импорта

`ImportOptions(document_limits=DocumentLimits(max_nodes=200000))` задаёт бюджет
модели для интеграционной диагностики читателей, финальной проверки и JSON загрузки.
`ImportResult.document_limits` сохраняет его для `lossless` и `assessment_complete`.
Превышение в этих фазах возвращает `document=None` и `import.document-limit`;
issue содержит источник и известный адрес, `measurement.limits`, а при известной
диагностике модели — `quota` и `maximum`. Неизвестный текст ошибки не превращается
в выдуманный адрес квоты. Ошибки повреждённого исходника остаются исключениями.

## Бюджет публичного экспорта

Базовый лимит 100000 узлов сохранён. `ExportOptions(document_limits=...)`
передаёт выбранный бюджет в встроенные DOCX/PPTX/HTML/EPUB/LaTeX/PDF обработчики,
JSON сериализацию и проверку готового JSON. Нативные обработчики используют
keyword-only `limits=...`; существующие сторонние writer(document, path)
сохраняют свой интерфейс и отвечают за собственные внутренние операции.

Встроенные операции integration, обход закладок, outline, подготовка шрифтов,
частное представление унаследованного цвета и HTML/PDF renderer используют этот же бюджет. Он
проверяется и для подготовленной модели: допустимый исходник может получить
расположенный отказ, если обработка создаёт модель сверх выбранной квоты.
Частное цветовое представление проверяется после материализации всех цветов;
возрастание модели не обходится сохранением исходного результата проверки.
`export.document-limit` содержит назначение и известный адрес;
`report.metrics['document_limit']` хранит выбранные `limits`, а для известного
сообщения SDK — `quota` и `maximum`. Неизвестное сообщение сохраняется целиком,
адрес квоты не угадывается. Даже после записи частичных staged bytes прежнее
назначение сохраняется, временный результат удаляется.

Собственный PPTX с 35 слайдами и 6720 уникальными текстами проходит два нативных
цикла с 200000 узлов. Шесть нативных форматов принимают собственную большую
модель с выбранным бюджетом 300000, сохраняя текст; default 100000 отказывает.
Большой DOCX проходит частное цветовое представление HTML/PDF/PPTX с 500000
узлов, не меняя исходную модель. Это приёмка бюджета и данных, а не доказательство
точности нативной компоновки. Отмена из публичного API передаётся внутрь PDF writer.

Выбранный бюджет модели не отменяет фиксированные пределы нативных профилей и
не ограничивает всю работу каждого парсера. Отмена до и после читателя проверяется
отдельно; полный контроль работы/ресурсов и отмены внутри всех обработчиков
остаётся в [TODO](../development/todo.md).
