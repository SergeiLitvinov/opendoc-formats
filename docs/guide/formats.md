# Форматы и ограничения

## Общая предпочтительная ширина DOCX

Таблицы и ячейки заполняют контракт `WidthMeasure` из `opendoc_model`.
`dxa` преобразуется в points, `pct` — в долю: для таблицы относительно области
страницы без полей (`content`), для ячейки относительно таблицы (`table`).
`auto`, `nil`, нулевая и отсутствующая ширина остаются различимыми. Это предпочтение,
а не измеренный результат раскладки. Единицы соответствуют
[описанию Microsoft OOXML](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.wordprocessing.tablewidth?view=openxml-3.0.1).

```python
from opendoc_model import WidthMeasure, get_preferred_width, set_preferred_width

width = get_preferred_width(table)
set_preferred_width(table, WidthMeasure("relative", 0.8, "ratio", "content"))
set_preferred_width(cell, WidthMeasure("absolute", 120, "pt"))
set_preferred_width(cell, None)  # убрать предпочтение, а не записать нулевую ширину
```

Неизменённое значение сохраняет исходную строку `docx_preferred_width`.
Явная правка общей ширины переопределяет её; `docx_width_imported` фиксирует
импортированный контракт и позволяет отличить удаление от прежнего JSON без него.
Старые JSON следует открывать через `read_document`: это заполняет общий контракт
до редактирования, включая вложенные таблицы и колонтитулы, без изменения файла.
Прямое декодирование моделью сохраняет прежние свойства; writer умеет их читать,
но для удаления предпочтения в таком старом объекте нужно убрать также native
`docx_preferred_width`. `set_typed("width_twips", ...)` продолжает поддерживаться;
непосредственное создание противоречащих дубликатов отклоняется моделью.
Отрицательная native ширина сохраняется как форматное расширение без выдачи
за неотрицательное значение общего контракта. Неверная запись
не заменяется приблизительным значением. Writer сохраняет исходную модель.

## Inline-изображения в PDF

Для inline-растров в PDF проверяется фактическая рамка Story: размеры должны
совпасть с заявленными после crop/rotation, изображение — помещаться в контейнер
и область страницы без полей. Переполнение не считается успешным только потому,
что весь текст остался в PDF. В ячейке переносится вся внешняя таблица; если
на новой странице она всё ещё не помещается, прежний файл назначения сохраняется.
Для измеренной DOCX-сетки PDF использует пропорции колонок, включая spans и
вложенные таблицы. Обычный HTML-export не получает CSS этого PDF-профиля.
Полная нативная пагинация таблиц Word не подтверждена: `pdf-table-flow-layout`
остаётся явной LOSS. Результаты — в [приёмке изображений в ячейках](../development/pdf-cell-images-evidence.json).

### Текстовый профиль DjVu

DjVu читает скрытый текстовый слой DjVuLibre как строгий UTF-8. Пустой слой
и одни разделители страниц не создают успешную пустую модель. Низкоуровневый
`read_djvu` возвращает пустой `Text` с warning при отсутствии backend, ненулевом
exit code, timeout или отсутствии текста; реестр в этих случаях поднимает
`ExtractError`. Повреждённый UTF-8 вызывает `InvalidDocumentError`, превышение
лимита — `ResourceLimitError`, отмена во время процесса — `OperationCancelledError`.

По умолчанию timeout составляет 30 секунд, общий лимит stdout/stderr — 10 MiB.
`read_djvu(..., timeout=..., max_output_bytes=..., cancelled=...)` позволяет
настроить эти ограничения; реестр передаёт `ImportOptions.cancelled` и применяет
общие ограничения входного файла и модели. Проверка отмены выполняется каждые
20 ms между чтениями процесса, без обещания жёсткого времени реакции ОС.
Страницы, координаты слов, изображения, OCR и обратная запись относятся к OF11.
Внешний DjVuLibre распространяется отдельно под GPL-2.0-or-later;
новых Python-зависимостей этот профиль не добавляет.

Неизвестный ID возвращает `import.unsupported-format` / `export.unsupported-format`.
Отсутствие Python-движка — `*.backend-unavailable`. Для TXT/JSON движки не нужны.
`DocFormat` в низкоуровневом извлечении текста перечисляет и идентификаторы низкоуровневых маршрутов;
перечисление само по себе не означает наличие маршрута в реестре.

## Проверка результата

### Текст PDF и небольшие страницы

PDF writer использует поток текста. Извлечённый PDF bbox — измерение исходных
glyphs, а не допустимая ширина строки после изменения шрифта. Для абзацев с PDF
provenance эти размеры не ограничивают поток; `pdf-text-layout` LOSS указывает
на изменение компоновки. Собственная страница 240×200 pt сохраняет весь plain
text относительно оригинала в двух публичных PDF/JSON циклах при поворотах
0/90/180/270. Это приёмка текста, не исходных координат и шрифтов.

Перед публикацией извлекается native text результата. Последовательные TextRun
проверяются с NFKC-нормализацией, игнорированием whitespace и soft hyphen;
каждое найденное вхождение расходуется отдельно. Основной поток объединяется
между страницами отдельно от областей колонтитулов. Проверка обнаруженного
пропуска возвращает `pdf-text-content` ERROR с адресом `.content[...]` и не
заменяет предыдущий файл. Максимум на секцию: 2 млн исходных и 4 млн извлечённых
символов, 100 тыс. фрагментов и 100 млн суммарной длины поисковой области;
превышение даёт `pdf-text-limit` ERROR. Формулы, изображения, chart labels,
native forms и annotations имеют отдельные профили и диагностику. Совпадение
normalised occurrences не доказывает reading order, видимость glyphs, точность
компоновки или сохранность всей PDF-спецификации.

В сгенерированных Story PDF восстанавливаются отсутствующие Unicode-соответствия
лигатур из встроенного OpenType GSUB. Поддерживается Type0/Identity-H с
CIDFontType2 и тождественным CID→glyph mapping: компоненты должны иметь
единственное Unicode-кодирование, а лигатура — единственную последовательность.
Изображение глифов и shaping не изменяются; повторные `fi`/`ti` на собственном
синтетическом шрифте сохраняют текст и все RGB-пиксели. Неоднозначные либо
неизвестные соответствия не угадываются; проверка текста остаётся обязательной.
Используется уже необязательный FontTools профиля `fonts`; без него эта обработка
недоступна. Пределы на секцию: 200 шрифтов, 20 МБ на шрифт и 50 МБ суммарно;
превышение возвращает `pdf-unicode-limit` ERROR. Разбор GSUB ограничен 1000
lookups, 100 тыс. лигатур и 32 компонентами; неподдержанное описание не исправляется.
Unicode stream больше 2 МБ либо нетождественное CID→glyph mapping не изменяются.
Это обработка собственного результата, не универсальный ремонт произвольного PDF.

### Позиционированный растр PDF

Каждое размещение PDF-изображения сохраняется, включая повторный xref на той же
или другой странице и inline images. `Image.box` содержит полную геометрию до
обрезки; viewport страницы задаёт видимую область. Исходная матрица размещения
проходит JSON в `Image.properties["pdf_image_transform"]`, soft mask объединяется
с пикселями в PNG с alpha. Полнота graphics state PDF этим не заявляется.

При записи изображение с явным `box` размещается нативно: bytes изображения
не пересэмплируются. Поддержаны отдельные масштабы осей, конечная невырожденная
affine matrix, shear, reflection и произвольный поворот. Без исходной PDF matrix
`box` задаёт неповёрнутую рамку, а `box.rotation` — поворот по часовой стрелке
вокруг её центра. С `pdf_image_transform` box задаёт bbox исходных осей;
изменения x/y/width/height масштабируют это размещение, rotation добавляет поворот.

`ImageCrop` задаёт неотрицательные доли от сторон изображения с непустой
видимой областью. Writer применяет нативный quadrilateral clip, без создания
новой картинки. Reader распознаёт ограниченный изолированный stream одного
image placement с таким clip; другие операторы, вложенные Form XObjects и
общий graphics state не относятся к этому профилю. Дополнительный разбор
ограничен 16 KiB кодированного и распакованного stream.

Inline DrawingML-изображения получают фактические позиции и страницы после
компоновки Story, включая выравнивание и колонтитулы. Paragraph-relative anchor
с нулевыми offsets и column/margin alignment следует потоку с
`pdf-raster-anchor-wrap` LOSS: floating wrapping/overlap не воспроизводятся.
Смешанный текст/изображение в строке даёт `pdf-inline-raster-layout` LOSS;
неподдержанные эффекты — `pdf-raster-effects` LOSS. Это конечный профиль,
без обещания исходной пагинации любого Word-документа.

Если фактическая рамка inline изображения в отдельном body-абзаце выходит
за нижнюю границу content box, writer переносит весь абзац на следующую страницу
и повторяет компоновку. Размер, crop/rotation и выравнивание изображения
не меняются; `pdf_flow_page_breaks` перечисляет source locations переноса.
Не более 32 повторов на секцию; повторное переполнение того же абзаца даёт отказ.
Промежуточные PDF закрываются, координаты якорей и изображений берутся только
из принятой компоновки. Сигнал отмены проверяется перед каждым проходом.
Ячейки таблиц и разбиение одного смешанного абзаца находятся вне этого исправления;
проверка `pdf-text-content` остаётся обязательной перед публикацией.

Извлечение ограничивает растр до 128 млн пикселей, 32768 по стороне, 32 MiB
кодированных bytes и 10000 размещений. Writer проверяет bytes, число размещений
и размеры PNG по заголовку; эти проверки не гарантируют жёсткий предел памяти
декодеров всех image formats. Невырожденность matrix, допустимая обрезка и
вместимость inline-рамки проверяются до публикации результата; отказ
`pdf-raster-unsupported` указывает расположение и сохраняет прежний файл.

Смешение фиксированных изображений с flow-текстом или нативными векторами даёт
`pdf-raster-compositing` LOSS: исходный paint order не восстановлен. Arbitrary
clipping текста/изображений и blend/masks graphics state остаются в OF07.
Общий контракт MediaBox/CropBox описан ниже. Для собственного конечного растрового профиля два PDF → JSON → PDF
цикла сохраняют image geometry и все RGB pixels, включая affine, поворот страницы,
обрезку и прозрачность. Независимый Form-reference подтверждает поворот/обрезку;
различия антиалиасинга допустимы только на границе clip.

Прямоугольная обрезка векторного Form XObject сохраняется отдельным стеком
областей `clip_rects` в свойствах vector resource. Writer применяет его к
собственному drawing stream; два PDF/JSON цикла проверены по всем RGB исходника
с CropBox и поворотами 0/90/180/270 в MuPDF и Poppler. Криволинейные clips и
группы прозрачности получают расположенный `pdf.vector-graphics-state` LOSS
и opaque исходник. Без подходящего visual surrogate writer отказывает,
сохраняя прежний файл. Это не поддержка полного PDF graphics state.
Рисунки аннотаций и widgets учитываются отдельно через interaction ledger;
они не дублируются в page vectors. Извлечение не меняет исходный PDF.

### Общая геометрия страниц PDF

`get_page_geometry(get_integration(model).pages[i])` возвращает общий
`PageGeometry`: MediaBox, необязательный CropBox и поворот до отображения.
`DocumentPage.width/height` равны размерам media до поворота, а не viewport.
Source coordinates заданы x=PDF x, y=-PDF y: ось y направлена вниз, начала
могут быть ненулевыми и отрицательными. Рамки элементов и аннотаций сохраняют
прежние crop-local координаты; явное преобразование не происходит автоматически.

Native writer помещает собственное отрисованное содержимое в исходные области,
сохраняя MediaBox/CropBox и поворот. Общая декларация имеет приоритет над
`source_rotation`; typed crop/rotation edits применяются как обрезка/поворот,
без принудительного переноса координат модели. `with_page_geometry(page, None)`
не восстанавливает прежние native поля: выход использует плоский viewport без
исходного поворота. Физическая страница связана с секцией через native
`section.properties["pdf"]["page_id"]`; непривязанный общий page получает
`pdf.page-geometry` LOSS. Repagination получает `pdf.page-geometry-pagination` LOSS.

Старый JSON без исходных MediaBox не позволяет восстановить скрытые размеры:
декларация остаётся неизвестной, прежние fields/JSON сохранены. Новые JSON
сохраняют tagged geometry, неизвестные extra и явное удаление. Полные
UserUnit, ArtBox/TrimBox/BleedBox и содержание вне прежнего viewport остаются в OF07.
При UserUnit ≠ 1 reader сохраняет исходный PDF и записывает located opaque
`pdf.page-geometry`/`unsupported-user-unit`; неверная tagged geometry не создаётся.
Для собственного растрового профиля сравниваются два PDF/JSON цикла: native
regions, page rect/rotation и все RGB pixels, включая отрицательные origins.

[PyMuPDF о MediaBox/CropBox](https://pymupdf.readthedocs.io/en/latest/glossary.html#mediabox)
описывает разные координатные соглашения backend-а; адаптер преобразует их
в общий top-down контракт явно, без зависимости от layout engine heuristics.

### Оглавление и закладки PDF

Reader заполняет общий `Outline` модели: иерархию, sibling order, page/external
назначения, provenance, point и zoom. Point задан до поворота в исходной media
системе координат; crop origin и стабильный page ID удерживаются в native
section profile. Неизвестные destination fields остаются в extra, исходный PDF
сохраняется непрозрачно. Модель не выполняет переходы и actions.

Writer создаёт native PDF bookmarks, сохраняя title/hierarchy и конечные
appearance fields bold/italic/color/collapse. Page IDs связываются с выходными
секциями; point применяется только при проверенной одностраничной геометрии.
Если исходный layout repaginated или его координатная связь неизвестна,
page destination сохраняется, а пропуск point получает
`pdf.outline-point` LOSS. Paragraph anchor использует действительную позицию
в основном потоке Story; другие kinds/нерасположенные anchors остаются без
назначения с `pdf.outline-target` LOSS. Неизвестное назначение не заменяется
первой страницей. Поддержаны URI http/https/mailto; launch, JavaScript, remote
files и произвольные actions не воспроизводятся.
При неоднозначном page ID после объединения документов назначение не угадывается:
текст и иерархия сохраняются, закладка получает `pdf.outline-target` LOSS.

Публичное чтение старого JSON переносит `pdf_outline` на общий контракт один раз.
Типизированные правки и удаление имеют приоритет над raw extension. Без известного
legacy crop origin point остаётся неизвестным; raw destination сохранён в extra.
Занятый непрозрачный `opendoc.outline` не перезаписывается. Полный профиль
named destinations/actions и media/crop структуры остаётся в OF07.

[PyMuPDF native TOC API](https://pymupdf.readthedocs.io/en/latest/document.html#Document.set_toc)
создаёт иерархию; собственные вновь созданные page actions записываются в PDF
coordinates для точности при всех четырёх поворотах. Это конечная геометрическая
приёмка, без обещания исходной компоновки текста любого PDF.

### Наследуемые свойства и осевые линии PPTX

Для явного `bgPr` фон выбирается по цепочке slide → layout → master:
ближайшая декларация имеет приоритет, включая `noFill`. Сплошной цвет переносится
в модель и применяется к выходному слайду; это сохраняет видимый цвет, а не исходную
структуру наследования. Градиент читается, но при записи упрощается с LOSS.
Полное разрешение style matrix/bgRef и custom theme остаётся в OF06.

Горизонтальные и вертикальные DrawingML freeform paths с нулевой шириной или высотой
не отбрасываются и не получают искусственную толщину bounding box при записи.
Путь и stroke остаются редактируемыми. Отрицательные размеры и нулевые обычные
фигуры по-прежнему не относятся к этому профилю.

Если цвет текста не задан, writer не создаёт пустой `solidFill`: цвет может
наследоваться от темы таблицы. Явные цвета сохраняются отдельно. Полный перенос
тем, встроенных table styles, master/layout и их отношений пока не обеспечен;
диагностика возможных различий темы таблицы остаётся. Два JSON roundtrip проверены
по XML и нативным свойствам PowerPoint на собственных слайдах.

### Ширины таблиц и smartTag в DOCX

Прямое оформление границ использует `get_borders`/`set_borders`/`set_border`
из opendoc-model 0.13.0. Таблица хранит четыре внешние и две внутренние стороны;
ячейка — четыре внешние и две диагонали. Поддержаны solid/dashed/dotted/double/
dash-dot/dash-dot-dot, RGB, толщина в восьмых пункта, целочисленный отступ,
различные явные подавления `none` и `nil`. Отсутствующая сторона остаётся
неопределённой; наследуемый стиль не материализуется в прямое оформление.
Правки и удаление имеют приоритет над исходными атрибутами. Два DOCX/JSON цикла
сравниваются с исходником; Word подтверждает свойства шести single borders
и нативное изменение double/red с последующим циклом. Word может нормализовать
эффективную толщину двойной линии: это декларация OOXML, не расчёт отображения.

Theme color, shadow/frame и неизвестные стили остаются в inert native extras
с `docx.table-borders` LOSS. Полный conditional style cascade, RTL start/end
и разрешение конфликтов соседних границ не реализованы. Непредставимые размеры
отказывают с расположенным ERROR без замены прежнего файла. Writers других
форматов сообщают `table-borders` LOSS; JSON сохраняет общий контракт.

Читатель учитывает theme references ASCII/hAnsi при определении Latin family
на соответствующем уровне run/character/paragraph style. Для конфликтующих
деклараций темы и literal fallback собственный Calibri 12 bold проверен
в Word 16.0.17932 относительно оригинала через два DOCX/JSON цикла.
Прямое оформление и character style перекрывают paragraph style; ссылка
hAnsiTheme не заменяет отдельную explicit ASCII family. Полные Unicode/language
font-slot rules, неизвестные темы, перенос между системами без изменения
семейства и полная визуальная приёмка остаются OF05.
Правила выбора шрифтов Word описаны в
[MS-OI29500 §17.3.2.26](https://learn.microsoft.com/en-us/openspecs/office_standards/ms-oi29500/aef3c9a6-5d6c-434b-90b7-85e761fd8e62).

HTML/EPUB используют ограниченную CSS-проекцию: четыре внешние стороны таблицы,
внутренние горизонтальные/вертикальные разделители и четыре прямые стороны ячейки.
Прямое оформление ячейки перекрывает соответствующий разделитель; `none`/`nil`
проецируются в отсутствие линии. Логические столбцы учитывают rowspan/colspan.
Поддержаны solid/dashed/dotted/double, цвет и толщина; диагонали, сложные штрихи,
native offsets и неизвестные параметры получают located LOSS. Отдельные CSS
границы не воспроизводят правила конфликтов Word. Общий `table-borders` LOSS
сохраняется: native declarations, различие подавлений и обратный семантический
импорт CSS не гарантируются. Непредставимые размеры и превышение лимитов
сетки дают атомарный отказ. Проверяется выходная CSS-структура собственного
HTML/EPUB fixture; равенство отображения в различных браузерах не заявляется.

DOCX сохраняет предпочтительную ширину таблицы и ячеек в исходных единицах
`dxa`, `pct`, `auto`, `nil`, включая процентную запись `100%`. Значения хранятся
в `properties["docx_preferred_width"]` как `{ "type": "pct", "value": "500" }`
и проходят JSON. Число `500` для `pct` означает 10% (единица — 1/50 процента).
Явное `TableCellProperties.width_twips` при экспорте задаёт абсолютную ширину
и имеет приоритет над исходным preferred width. Grid widths сохраняются отдельно.

Вложенный текст `w:smartTag` остаётся доступен в модели, а исходная XML-оболочка
переносится обратно в DOCX. Диагностика `docx.smart-tags` имеет state `opaque`:
сохранение оболочки не означает семантического редактирования smart tag.
Два цикла DOCX → JSON → DOCX проверены по исходному XML и в Word на собственных
примерах. Это конечная проверка, не обещание одинаковой пагинации любого DOCX.

### Профиль записи EPUB

`write_document(model, "book.epub")` использует собственный MIT writer и стандартную
библиотеку Python; `epub`, EbookLib и lxml для записи не нужны. EPUB 3 содержит
container/OPF/nav, XHTML документ на каждую секцию в spine и оглавление из заголовков.
Оглавление вложено по уровням заголовков; пропущенные уровни прикрепляются к
ближайшему предыдущему заголовку меньшего уровня.
Секции идут последовательно как главы; ссылки между ними переписываются.
Missing/ambiguous fragment targets становятся inert links с диагностикой потери.
Абзацы, стили, списки, таблицы с объединениями,
MathML и внутренние ссылки используют общий HTML renderer. PNG/JPEG/GIF/SVG сохраняются
как локальные manifest assets; повторные изображения дедуплицируются по байтам.
Другие image media types отклоняются без замены существующего результата.

Действуют диагностика HTML renderer, ограничения XML (128 уровней, 100 000 элементов),
64 MiB для XHTML, изображений и готового архива, а также `ExportOptions` для проверки
модели и отмены перед публикацией. ZIP CRC, mimetype, package/spine и XML проверяются
до атомарной замены файла. Это структурная проверка, не EPUBCheck и не доказательство
одинакового отображения во всех reading systems. Контейнер использует stored ZIP entries.

Исходный package, неподключённые attachments и nonsemantic source ledger не
восстанавливаются молча: отчёт содержит потери. Reflow/fixed layout и сложная исходная
навигация не обещаются; writer всегда отмечает границу layout profile.
Шрифты следуют общему font preflight/embedding profile и правам на конкретный font asset.
Обычный и rich fixture с двумя главами проходят отдельную
[EPUBCheck acceptance](../development/epubcheck.md) в CI. Расширение metadata/navigation
profiles для исходных EPUB (refinements, page-list/landmarks, fixed layout) относится к OF08.

### Метаданные EPUB

`metadata.epub.dc` содержит списки текстовых значений Dublin Core; повторяющиеся
значения сохраняются через EPUB/JSON. Writer поддерживает title, language, identifier,
creator, contributor, subject, description, publisher, date, type, format, source,
relation, coverage и rights. Явные одноимённые поля в `DocumentModel.metadata`
переопределяют импортированные значения; совпадающие primary title/language/identifier
сохраняют дополнительные значения. Первый title/language используется в XHTML.
При отсутствии identifier создаётся SHA-256 identifier содержимого глав.

```python
model.metadata.update({
    "title": "Моя книга", "language": "ru", "identifier": "urn:example:my-book",
    "creator": ["Первый автор", "Второй автор"],
    "publisher": "Издатель", "subject": ["Документы", "Форматы"],
    "description": "Описание книги", "rights": "Права на эту книгу",
})
```

Допускаются строки или непустые списки строк, не более 1024 значений, 65 536 символов
в одном значении и 1 MiB суммарного UTF-8 текста. Недопустимые XML characters и
некорректные типы дают error; неизвестные ключи внутри `epub.dc` — loss с location.
Атрибуты и OPF refinements остаются в original XML snapshot и не объявляются
восстановленными семантически. Язык должен быть корректным языковым тегом EPUB;
исчерпывающую conformance проверку выполняет внешний EPUBCheck профиль.
Структура ориентирована на [спецификацию EPUB 3.3](https://www.w3.org/TR/epub-33/).

### Профиль TXT

Нативные TXT reader/writer поддерживают кооперативную отмену внутри обхода
абзацев/таблиц и обработки переводов строк с сохранением прежнего назначения;
границы и API описаны в [ресурсах и отмене](resources.md#отмена-txt).

```python
from opendoc_formats import ExportOptions, ImportOptions, TextProfile, read_document, write_document

# CP1251 без BOM требует явного выбора.
result = read_document("source.txt", options=ImportOptions(txt_profile=TextProfile("cp1251")))
if result.success:
    # auto на записи использует сохранённые encoding/BOM/newlines исходного TXT.
    report = write_document(result.document, "copy.txt", options=ExportOptions(txt_profile=TextProfile()))
```

`TextProfile.encoding`: `auto`, `utf-8`, `utf-16-le`, `utf-16-be`, `cp1251`.
Автоматическое чтение распознаёт UTF-8/UTF-16 BOM; без BOM применяется строгий UTF-8.
Это конечная политика, не распознавание произвольной кодировки. Legacy text и UTF-16
без BOM требуют явного выбора. Невалидные bytes, UTF-32, NUL, конфликтующий/запрещённый
или обязательный отсутствующий BOM отклоняются с `import.txt-encoding` и машинным `reason`.
CP1251 не имеет BOM. Декодирование и кодирование не заменяют ошибочные символы.

`bom`: `auto`, `require`, `forbid`. На записи `auto` берёт BOM исходного профиля,
если он сохранён; для новой модели BOM отсутствует. `newline`: `preserve`, `lf`, `crlf`, `cr`.
Модель хранит логические абзацы независимо от физических разделителей; низкоуровневый
`read_txt` применяет выбранную newline policy к тексту. Writer применяет её к выходным bytes.
`preserve` использует исходную последовательность разделителей, включая смешанные CRLF/LF/CR.
При изменении числа границ writer выбирает LF и сообщает `LOSS: txt-newlines`.
Без `ExportOptions.txt_profile` сохраняется прежний UTF-8/LF без BOM.

Исходные encoding/BOM/newlines, SHA-256 и размер находятся в `metadata.txt`;
сводка профиля — в provenance секции. JSON сохраняет оба представления.
Неизменённый TXT после JSON и записи с `TextProfile()` проверен байт-в-байт для всех
перечисленных кодировок. Непредставимые в выбранной кодировке символы отклоняют экспорт
до замены предыдущего файла. Проверка результата использует фактическую кодировку writer.
TXT сохраняет только основной текст; byte roundtrip не обещан для произвольной сложной модели.

### Отчёт импорта

EPUB использует конечный CSS profile: простые element/class/id selectors и текстовые
свойства font-family/font-size/font-weight/font-style/text-decoration/vertical-align,
color/background-color. Неподдержанные selectors/properties, at-rules/nesting,
malformed source, invalid font-size, var/calc/URL/important values и missing/remote
stylesheets диагностируются как `epub.css`. Поддержанные плоские правила сохраняются
рядом с неподдержанными группами; содержимое `@media` не применяется безусловно.
Linked CSS удерживается в raw resource (`opaque` с `resource_id`), ограничения inline
CSS отмечаются `lost` с исходным ID/строкой. Это частичная оценка, не полный CSS parser
или browser layout. Внешний stylesheet URL не загружается и не заменяется локальным файлом.

EPUB удерживает оригинальные `META-INF/container.xml`, OPF и manifest nav/NCX
как XML attachments. `metadata["epub"]["source_xml_resources"]` связывает действительное
имя части ZIP с resource ID; исходные байты и provenance сохраняются через JSON.
`epub.metadata_entries` содержит все дочерние OPF metadata XML entries, включая
повторяющиеся поля и `refines`, а `epub.package_properties` — атрибуты package.
Это исходные данные, не выполняемые инструкции. Ledger `epub.package` отмечает
`opaque` и проверенный ресурс. Иерархия навигации и rendition hints удерживаются
в источнике, но не являются полной редактируемой моделью nav или fixed-layout.

Нелинейные главы EPUB импортируются при явном выборе:

```python
from opendoc_formats import ImportOptions, read_document

result = read_document("book.epub", options=ImportOptions(epub_include_nonlinear=True))
```

Для прямого reader доступен `read_epub_model("book.epub", include_nonlinear=True)`.
По умолчанию `linear=no` пропускается с `nonlinear-spine` diagnostic. При включении
главы импортируются в порядке исходного spine; признак сохраняется в
`section.properties["epub"]["linear"]`. Metadata `epub.source_spine` содержит все
исходные idref/href/linear, а `epub.include_nonlinear` — выбранный режим, включая JSON.
Режим не добавляет поддержку nav или других неподдержанных spine item types;
оценка EPUB по-прежнему явно неполная.

EPUB также импортирует изображения вне абзацев и inline SVG в исходном порядке.
SVG очищается общим безопасным XML-путём и хранится как vector image resource;
ledger отмечает `opaque` с `resource_id`, поскольку редактируемые фигуры не построены.
Scripts, обработчики событий и внешние ссылки SVG не исполняются и не загружаются;
удаление из SVG диагностируется. Одинаковые SVG используют общий ресурс, а совпадение
ID с исходным manifest asset не приводит к его перезаписи.

Исходные font/audio/video assets удерживаются как `ResourceKind.ATTACHMENT` с
`opaque` record `epub.asset`: точные байты и provenance сохраняются через JSON.
Это не активация шрифта, обработка его обфускации, воспроизведение или гарантия
прав на сам asset; его лицензию следует учитывать отдельно от лицензии адаптера.
HTML export встраивает изображения и безопасный SVG, сообщает о невоссозданных
функциях EPUB и не активирует inert assets. `img` использует только локальный
image item из manifest; внешние URL и ссылки на файлы иных media types диагностируются.

Native EPUB также импортирует XHTML `table`/`caption`/`tr`/`td`/`th` в Table:
`rowspan` и `colspan` поддерживаются в диапазоне 1–100, недопустимые значения
заменяются единицей с loss diagnostic. Сохраняются вложенные таблицы и порядок
текста вокруг блоков в ячейках. Таблица внутри текстового блока (`p`, `li`,
`blockquote` и т. п.) пока уплощается с явным issue. Профиль ограничен
10 000 ячейками на таблицу, 16 уровнями таблиц и 64 уровнями контейнеров ячейки.
MathML сохраняется как Formula с inline/display признаком; опасные элементы и
атрибуты удаляются с диагностикой, JavaScript не исполняется. Provenance использует
реальное имя части ZIP, включая папку OPF. JSON и HTML export сохраняют проверенную
структуру; полный EPUB/CSS и writer EPUB остаются задачами. Профиль `epub` использует
собственный контейнер, стандартный XML и BeautifulSoup, без EbookLib/lxml.

## Формальная роль заголовка DOCX

DOCX использует общий контракт `Heading` модели: уровни 1–9 импортируются из
нативной структуры, включая наследуемый `outlineLvl` и document defaults.
Крупный/жирный текст не считается заголовком по оформлению. У встроенных
Heading 1–9 уровень фиксирован самим стилем: [правило Word](https://learn.microsoft.com/en-us/office/vba/api/word.paragraph.outlinelevel).
Прямое переопределение применяется к остальным стилям; `outlineLvl=9` означает
основной текст. Некорректный уровень вне 0–9 отклоняется.

Writer записывает явно заданную роль даже без именованного стиля. Явная смена
или удаление импортированной роли имеет приоритет над `docx_outline_level`.
При конфликте с фиксированным встроенным стилем создаётся производный стиль,
сохраняющий оформление; его определение включается в восстановленный styles part.
Два цикла через JSON проверены структурно и в Word, отдельно проверены
редактирование/удаление роли, текст, шрифт/размер/цвет и интервалы абзаца.
Это не обещание полной семантики сложного DOCX или всех эффектов оформления.

## Конечный профиль семантики HTML

HTML → JSON → HTML сохраняет язык документа и ближайший унаследованный `lang`
текстового фрагмента, включая пустой язык. Подпись возвращается внутрь `caption`,
сохраняя текст, inline styles и ссылки. Переносятся `th`/`td`, `scope=col/row/rowgroup`,
идентификаторы ячеек, связи `headers`, объединения и отдельные группы
`thead`/`tbody`/`tfoot`. Заголовки документа, списки и внутренние ссылки также
сохраняются в проверенном статическом профиле.

HTML заполняет общие `TableSemantics`, `TableRowSemantics` и `TableCellSemantics`:
роли header/data, scope, headers и группы строк. `caption_ids` связывают таблицу
с общими якорями редактируемых Paragraph, включая пустую подпись. Подпись может
находиться отдельно от таблицы; writer выводит её один раз. Общие правки и
явное удаление имеют приоритет над сохранёнными исходными атрибутами.
Неоднозначные повторяющиеся IDs и отсутствующие header targets получают
расположенную диагностику; текст и исходные расширения сохраняются без
выдуманных общих связей. Старые JSON мигрируют однократно; маркеры отличают
прежние данные от явного удаления. Группы столбцов задают логические интервалы,
включая `scope=colgroup`; объединения строк/столбцов учитываются при проверке
принадлежности. Необъявленные столбцы не получают выдуманных групп.
Профиль ограничен 10 000 логическими столбцами и 100 000 проверками grid intervals;
оформление отдельных `col`/`colgroup` диагностируется как неподдержанное.
Собственная схема документа не вводится: используется JSON OpenDoc Model.

Полная ARIA-семантика, `role` и `dir` вне профиля получают
located `html-accessibility` loss. Исключение — уже поддержанное имя inline SVG
через `aria-label`. Оригинальные bytes остаются inert attachment; это не
сохранение интерактивного поведения. Проверены две структурные итерации,
экранирование атрибутов и вложенные таблицы. Полная проверка браузерного дерева доступности,
экранного диктора и адаптивного layout остаётся в OF10; полнота HTML не обещается.
Независимое свидетельство для опубликованного HTML-профиля подтверждает
имя таблицы, columnheader/rowheader и внутреннюю клавиатурную навигацию
после двух циклов в Chromium 151 при ширинах 375/1280. При 375 остаётся
горизонтальная прокрутка фиксированной страницы; screen-reader acceptance не измерена.
Новых зависимостей профиль не требует: `html` сохраняет MIT BeautifulSoup и
BSD-3-Clause tinycss2, согласно [лицензиям профилей](dependencies.md).

HTML дополнительно записывает выявленные ограничения статического профиля в
`opendoc.integration`: `lost` относится к неперенесённой семантике, CSS или ресурсу,
а отдельный `opaque` record `html.source` — к оригинальному файлу HTML.
При наличии предупреждений его байты сохраняются в attachment
`html-original-source`; это не подтверждает загрузку внешних assets и не означает
сохранение browser behavior. JavaScript и обработчики событий не исполняются.
Ledger содержит исходный файл, строку/колонку при наличии, ID элемента и
`extra.block_location` для связи с прежними HTML diagnostics. HTML → JSON сохраняет
оба представления; HTML writer сообщает о невоссозданных исходных функциях и
не вставляет source attachment в страницу. Копия ограничена 10 MiB, предупреждения —
10 000 объектами. Пустой ledger не является полной оценкой HTML/CSS.

`ImportResult.issues` объединяет предупреждения читателя из `metadata.warnings`
и `metadata.<format>.warnings` с записями `opendoc.integration`.
Строковые предупреждения получают код `<format>.warning` и путь к исходному файлу
с адресом записи в metadata; структурированные HTML-предупреждения сохраняют свой код
и location. Исходная metadata остаётся в модели и сохраняется через JSON.

Для typed ledger состояния `opaque`, `visual` и `lost` дают `LOSS`,
`rejected` — `ERROR`; reason, location и измерения сохраняются.
Отказ в сохранении объекта делает `success=False`, но прочитанная модель остаётся
доступной для анализа. `assessment_complete=True` требует явно завершённой оценки
и отчёта для каждой заявленной функции. `lossless=True` дополнительно требует
семантического сохранения всех оценённых функций и отсутствия `LOSS`/`ERROR`.
Это оценка заявленного профиля, а не всей спецификации формата.
Без ledger импорт может быть успешным, однако не считается проверенным без потерь.
Строковые предупреждения не превращаются автоматически в оценку сохранности:
полнота диагностики внутри читателей остаётся задачей [OF15](../development/todo.md).

EPUB reader записывает частичную оценку в `opendoc.integration`: пропущенные
нелинейные/неподдержанные spine items, выходы за профиль таблиц/MathML,
изображения без локального image ресурса и audio/video playback, object/script.
Это состояние `lost`,
даже когда часть текста или alt сохранилась. `reason` описывает конкретную потерю;
`location` содержит исходный файл, часть архива и ID элемента либо строку/колонку XHTML.
Provenance сохраняет исходную часть и ID. Исходные font/media assets и inline SVG
удерживаются `opaque` с проверенным ресурсом; их байты не объявляются потерянными.
Полный CSS, OPF metadata, accessibility
и другие функции ещё не оценены: `assessment_complete` остаётся `False` для EPUB.

PPTX reader сохраняет частичную оценку: исходный package graph не перенесён,
transition/timing, иерархия групп, audio/video playback и 3D settings потеряны;
фигуры без разрешимой геометрии/положительного extent и картинки без ресурса
отмечены как пропущенные. Для неподдержанного graphic object (включая OLE/диаграмму
SmartArt) `visual` означает фактически сохранённую картинку предпросмотра с `resource_id`;
`lost` — отсутствие такой картинки. Payload OLE и исходные связи из этого не следуют.
Диагностика содержит source path, фактический part name, XPath, source shape ID
и номер слайда. Путь к части не вычисляется из номера слайда, поэтому перестановка
слайдов не искажает адрес. JSON сохраняет ledger и provenance.
Полнота тем, master/layout, chart data и других функций ещё не оценена;
`assessment_complete` остаётся `False`, а OF06/OF15 остаются открытыми.

DOCX reader оценивает сложные исходные объекты: comments/revisions/content controls,
fields, text boxes/WordArt, SmartArt/OLE, protection и соответствующие связи.
`opaque` означает проверенное совпадение сохранённого XML-фрагмента либо сохранение
части в PackageGraph; это не полноценная семантическая модель диапазона, объекта или поля.
Проверка фрагментов учитывает их кратность и каноническое XML-представление;
байтовая идентичность всего исходного DOCX из этого не следует. Отсутствующий фрагмент
отмечается `lost`, даже если inventory классифицирует тип как `native-ooxml`.
Поле `docx_features.assessment_scope` явно отделяет учёт типов от доказательства
сохранности в `opendoc.integration`.

Для связанного непрозрачного объекта проверяются байты target part и соответствующая
связь в PackageGraph; внешняя OLE-ссылка не считается перенесённой и не загружается.
Issue содержит исходную часть, XPath или relationship ID, provenance — source path и ID.
JSON сохраняет эти сведения. Импорт и экспорт не исполняют embedded payload или поля.
Оценка остаётся неполной (`assessment_complete=False`); OF05/OF15 открыты.

### Интерактивный профиль PDF

`opendoc.integration` содержит `DocumentPage`, `Annotation` и `FormControl`:
links с inert destination, Text/FreeText notes, highlights с исходными vertices,
text/checkbox/choice/button widgets с именем, value, choices и flags. Scripts и
сырые `A`/`AA` сохраняются как строки/данные, не исполняются и не разыменовываются
во внешние файлы/URL. Это конечный профиль; сложное appearance и редактируемая
иерархия полей не обещаются. Outline имеет отдельный общий контракт и нативный профиль.

Writer создаёт URI links, Text notes, highlights с подтверждёнными quadrilaterals
и текстовые поля AcroForm при однозначной связи исходной страницы с единственной
выходной страницей. Совпадение canonical field values и widgets проверяется
независимыми движками. Два PDF/JSON цикла относительно оригинала и нативная правка
поля проверены на обычной/240×200 pt странице при всех четырёх поворотах.
Прямые изменения текста/значения и удаление объектов не восстанавливаются из backup.
Исходные номера xref не переносятся. Поддержанный одиночный JavaScript `A` текстового
поля переносится как inert source data; цепочки и дополнительные actions получают
расположенный LOSS. Код библиотека не исполняет. Неподдержанные виды полей/аннотаций
и неизвестная геометрическая связь имеют отдельную диагностику.

Rich import извлекает основной текст и векторы из отдельной несохраняемой копии
без widget/annotation appearances, чтобы не дублировать их при следующей записи.
Повторное открытие этой копии сбрасывает нативные caches, включая cross-page links.
Content view ограничен 128 MiB исходного файла, 256 MiB снимка и 10 000 objects.
Полный AcroForm field tree, все appearances/actions, legacy vertices без исходной
геометрии и независимый inspection text scope требуют дополнительной приёмки;
конечный C-PDF-01 остаётся открытым.

AcroForm `/Fields` и `/Kids` проверяются отдельно от page widgets: до 10 000
узлов и глубины 64, только явные indirect references. Циклы, повторное владение
и неверные ссылки отклоняют чтение. Parent fields, orphan fields и widgets вне
canonical tree имеют расположенный `pdf.field-tree` opaque record; иерархия
не считается восстановленной из совпадения widget values. Дополнительные свойства
и XFA/calculation order/signature flags имеют отдельные opaque records.
Строковый `/DV` обычного текстового поля хранится в `extra.pdf_default_value` и
переносится через JSON. Явное `None` удаляет default. Повторные поля с одинаковым
именем требуют согласованных value/flags/default; конфликт или default более
65 536 символов отказывает без замены предыдущего файла. Generated widget получает
связь `/P` с реальной страницей, чтобы оптимизация не объединила разные occurrences.
Собственные tests проверяют default/edit/delete, отдельные native xrefs на двух
страницах, parent/orphan diagnostics, циклы дерева и лимит.

Неизвестные типы annotations/widgets, structure tree, layers и catalog actions
получают состояние `opaque`, а исходный PDF сохраняется в Attachment
`pdf-original-source` (до 10 MiB). Для профильных объектов эта копия тоже сохраняется,
чтобы удержать оставшиеся source references и appearance. Она не исполняется.
Plain PDF без таких объектов не получает дополнительную source-копию.
Лимиты профиля: 10 000 записей, 65 536 символов в извлекаемых строках;
ошибка лимита отклоняет чтение, а не возвращает пустую модель.

Page/xref provenance и backup сохраняются через JSON. `assessment_complete=False`:
наличие source-копии не означает полного семантического чтения PDF. Layout writer
поддерживает перечисленные конечные interactions и отдельный outline profile;
остальные виды и opaque features имеют `LOSS`.
Другие writer profiles не получают обещания переноса этих объектов.

Координаты — точки в неповёрнутом cropbox; rotation находится в page extra и
`section.properties.pdf.source_rotation`. Writer восстанавливает этот поворот
после layout, сохраняя согласованность размеров и геометрии.
API и координатный контракт движка: [Page](https://pymupdf.readthedocs.io/en/latest/page.html),
[Annot](https://pymupdf.readthedocs.io/en/latest/annot.html),
[Widget](https://pymupdf.readthedocs.io/en/latest/widget.html).

`ExportOptions.verify_output=True` включает проверку временного файла **до** замены результата:

| Формат | Проверка |
| --- | --- |
| TXT | Декодирование UTF-8; пустой документ допустим |
| JSON | Повторная загрузка и валидация модели OpenDoc |
| HTML | UTF-8 и наличие внешней структуры html/head/body |
| DOCX / PPTX | CRC ZIP, разбор основных XML-частей, повторное открытие выбранным движком |
| PDF | Открытие, отсутствие шифрования, наличие страниц, чтение их текста |
| LaTeX | UTF-8, begin/end document; без компиляции |

Ошибка — `export.invalid-output`; предыдущий файл сохраняется. Отмена проверяется ещё раз после проверки.
Проверка читаемости не измеряет визуальное совпадение или редактирование в Microsoft Office.
У пользовательского экспортёра проверки нет, пока он не предоставит `ExporterSpec.validator`.
Отключить проверку можно через `ExportOptions(verify_output=False)`.

## Шрифты

При экспорте доступные шрифты выбираются из системы. Если запрошенного семейства нет,
выбирается замена с учётом начертания и покрытия символов; имя в результате может отличаться
на Windows и Linux. Выбор записывается в `report.metrics["font_resolution"]`, замена —
предупреждение `font-substitution`. Исходная модель при этом сохраняется.
Встраивание учитывает разрешения шрифта; отсутствие подходящего шрифта или глифов
диагностируется как потеря. `report.lossless` допускает предупреждения и не гарантирует
одинаковое визуальное отображение на разных системах.

При сохранении opaque OOXML в DOCX выбранные разрешённые font programs
встраиваются целиком: текст/начертания внутри native fragment могут отсутствовать
в семантических runs и потому не дают полного glyph inventory для subsetting.
Метрика `font_embedding.subset_policy` равна `full-for-retained-ooxml`;
обычный семантический документ использует `semantic-usage`. Это может увеличить
размер DOCX, но не удаляет FONT references и не скрывает `docx.smart-tags` LOSS.
Уже отсутствующие во входной программе глифы по-прежнему дают `font-glyphs` LOSS.
Полный выбор opaque-only faces и их каскад остаются
[C-FONT-OPAQUE-01](../development/format-requests.md#c-font-opaque-01).

## Отдельные конвертеры

`writers.pdf_to_docx` предлагает прямые движки PDF → DOCX; Pandoc/LibreOffice используются
только соответствующими маршрутами и устанавливаются отдельно.
`writers.docx_to_latex.DocxToLatexConverter` и `readers.latex.docx_to_latex_pandoc`
работают с DOCX напрямую. Lua-фильтр поставляется в пакете.

`writers.pptx_to_html.convert(input_path, output_directory)` создаёт локальный просмотрщик
со слайдами, CSS/JS, изображениями и извлечёнными OLE-объектами. Формулы выводятся в MathML,
поддержка отображения зависит от браузера. MathJax из сети автоматически не подключается.
Извлечённые OLE-файлы не исполняются библиотекой; просмотрщик предназначен для доверенных презентаций,
а не для изоляции произвольного активного содержимого.

Низкоуровневые конвертеры имеют собственные параметры и диагностику.
Политику чтения `ImportOptions` и записи `ExportOptions` обеспечивает вызов через
реестр. Файловая инспекция принимает собственный keyword-only `options`.

## Векторные ресурсы PDF

`application/pdf+vector` сохраняет команды `l`, `c`, `re`, `qu` и свойства paint.
PDF exporter выводит их нативно в координатах `Image.box` на первой странице секции;
векторные колонтитулы повторяются на её страницах. Поддерживается перенос и равномерное
масштабирование относительно исходного bbox; обводка и dash pattern масштабируются вместе.
Порядок наложения вектора следует порядку объектов модели поверх HTML-потока;
полное восстановление исходного PDF reading order, clipping/masks и ICC/blend остаётся OF07.

Предел — 50 000 команд на документ. Неизвестная команда, clip/mask/transform либо
неподдержанный paint требует явно заданного `Image.visual_surrogate` с PNG-ресурсом.
PNG ограничен 32 MiB, 8192 пикселями по стороне и 16 миллионами пикселей суммарно.
Такой fallback сообщает потерю редактируемости; без подходящего surrogate возвращается
ошибка без замены прежнего выходного файла. Исходная модель, команды и provenance
остаются доступны через JSON и не изменяются экспортёром.

## Бюджет файловой инспекции

```python
from opendoc_model import DocumentLimits
from opendoc_formats import ImportOptions
from opendoc_formats.support.inspection import inspect_path

report = inspect_path("slides.pptx", options=ImportOptions(
    max_input_bytes=30 * 1024 * 1024,
    document_limits=DocumentLimits(max_nodes=200_000),
))
if not report.valid:
    print(report.issues, report.metadata.get("document_limit"))
```

Выбранные `DocumentLimits` передаются чтению DOCX/PPTX/Model JSON и построению
инспекции модели, включая TXT. Обычный бюджет остаётся 100000 узлов. Собственный
PPTX 35 слайдов / 6720 runs и его Model JSON проходят с 200000, сохраняя точные
метрики, объекты и текстовый поток; стандартный бюджет даёт адресный отказ.
`inspection.document-limit` содержит исходный путь; `metadata.document_limit`
сохраняет `quota`, `maximum` и выбранные ограничения, включая нулевой byte budget.

Без `options` предел входа — 128 MiB, чтобы сохранить прежний потолок PDF;
явный `ImportOptions()` использует свой обычный предел 10 MiB.
`max_input_bytes` проверяется до чтения и при вычислении SHA256 блоками.
`inspection_source_sha256` — хеш байтов перед разбором, когда они были прочитаны
полностью. У успешно завершённой инспекции он повторно проверен после разбора.
Изменившийся источник даёт `inspection.source-changed`, измерения отбрасываются.
Хеш до разбора может оставаться у отказа; ранний отказ по размеру/отмене его не имеет.

`cancelled` проверяется до чтения, между блоками хеширования, между чтением и
инспекцией модели, после инспекции, а для PDF — перед каждой страницей.
Отмена возвращает `inspection.cancelled` без измерений. Прерывание внутри каждого
вызова стороннего декодера пока не гарантируется.

`metadata.inspection_status` различает `completed`, `partial`, `refused`, `cancelled`.
`completed` означает завершение выбранного алгоритма, а не полноту поддержки
формата. Ресурсные пределы внутренних native HTML/LaTeX/PDF алгоритмов остаются
отдельными; `DocumentLimits` не объявляется бюджетом памяти этих декодеров.
Сохраняются нативные метрики, геометрия и области измерений: PDF не подменяется
инспекцией промежуточной модели. Неполный native PDF text profile имеет `partial`
и не подтверждает сохранность текста даже при сравнении с собой.

## Нативная PDF-инспекция текста

`opendoc_formats.support.inspection.inspect_path(path)` работает с профилем
`pdf-rich`, без pypdf. Метаданные `text_flow` и `text_flow_profile` используют
контракты OpenDoc Model, а не собственную нормализацию. Область
`pdf-native-text-layer-v1` — весь текст, возвращённый PyMuPDF `get_text("text",
sort=False, flags=TEXTFLAGS_TEXT)` по страницам; сюда могут входить appearances
полей. Идентификатор профиля включает версию PyMuPDF. Сравниваются только
совместимые, измеренные и полные профили.

Рецепт сворачивает пробелы и границы страниц; Unicode, порядок слов и
лигатуры сохраняются. Это проверка извлечённого слоя, а не OCR, семантического
порядка чтения, видимости, верстки или формул. Полного object inventory нет:
`ObjectLossPolicy(0)` по такой инспекции остаётся непроверенной.

Лимиты: исходный файл 128 MiB, 10 000 страниц, 1 000 000 исходных символов
на странице, 10 000 000 суммарно. Лимит текста проверяется после нативного
извлечения; это не ограничение памяти внутреннего PDF-декодера. Пароль,
лимит и ошибка извлечения получают причину и исходную позицию. Непроверенный
или частичный профиль не проходит `TextPreservationPolicy("flow", 0)`, даже
если доступный текст совпал. Пустой измеренный слой отличается от неизвестного.

`form_fields` считает уникальные полные имена AcroForm по `/T`, `/TM` и
`/Parent`, включая именованные родительские узлы. `form_widgets` отдельно
считает widgets страниц. `pdf_field_names_complete` относится только к именам.
Профиль допускает явные indirect references поколения 0: максимум 10 000
узлов, глубина 64, имя 65 536 символов, массив ссылок 200 000 символов.
Цикл, повторное владение, прямой dictionary и неподдержанный тип дают
`pdf.field-inventory` по `catalog.AcroForm.Fields`; непроверенный `form_fields`
отсутствует. Это не восстановление полной иерархии, значений и событий AcroForm.

## Карта предоставленного PDF-surrogate

`get_object_mapping(report)` возвращает независимую типизированную копию
`ObjectMapping` OpenDoc либо `None`, если writer не предоставляет карту.
JSON в `report.metrics["object_mapping"]` использует общий versioned codec.
Профиль `pdf-vector-raster-routing-v1` охватывает только вхождения
неподдержанного PDF-вектора с предоставленным PNG-surrogate и автоматическую
SVG→PNG растеризацию. Полный инвентарь документа этим не подтверждается.
Исходная модель не меняется.

Source occurrence имеет отдельный report-local ID, исходный resource ID,
подтверждённый model anchor при наличии и копию provenance. Два вхождения
одного ресурса имеют разные occurrence IDs. Replacement — raster resource
в исходном snapshot; редактируемая векторная семантика обозначается потерянной
через `VISUAL`, LOSS, machine code/reason. Неподдержанный вектор без surrogate
имеет `REJECTED`. Эти состояния не выводятся из текста сообщения.

PDF writer связывает отдельные нативные вставки с source occurrences, затем
проверяет их после сохранения/оптимизации. Target locator содержит фактические
page/image indices, xref, bbox и digest изображения. Target model/resource ID
подтверждается свежим декодированием результата; typed anchor различает вхождения.
Если декодирование не подтвердило handle, native-only occurrence его не объявляет.
Неподтверждённые targets остаются unknown с адресной диагностикой.
`assessment_complete` относится только к объявленным fallback occurrences.
Повтор на нескольких страницах обозначается одной группой с несколькими
целями; произвольные split/merge не выводятся автоматически.

`result_id` — SHA-256 фактических PDF bytes. Временный путь не служит
идентичностью. Перенос неизменённого файла сохраняет карту. Внутренний writer
создаёт staged mapping; успешная атомарная замена переводит её в published.
Внешний `write_document` проверяет качество в staging до замены файла:

```python
from opendoc_formats import ExportOptions, get_object_mapping, write_document

report = write_document(document, "output.pdf", options=ExportOptions(
    quality_gate=lambda report, staged_path: report.lossless,
))
mapping = get_object_mapping(report)
```

Callback должен вернуть bool; false, исключение или ERROR в report запрещают
публикацию. Cancel/ошибка публикации дают rejected, изменение или удаление
staged bytes после измерения — invalidated. Actual targets/locators очищаются,
полнота сбрасывается. Произвольное изменение файла после успешной публикации
требует новой проверки идентичности, а не автоматического восстановления карты.

Кодек карты и нативная история проходят два полных PDF → модель → JSON → PDF
цикла, перестановку и удаление. В PDF хранится собственный инертный JSON stream
`OpenDocFormatsMapping`: максимум 8 МиБ сжатых и распакованных данных,
10 000 связей, только plain или FlateDecode без DecodeParms. Эти ограничения
относятся к истории, а не к памяти нативного PDF-движка.

`read_pdf_origin_mapping(path)` возвращает свежую типизированную карту либо
`None`, если подтверждённых связей нет. Исходное происхождение имеет профиль
`pdf-vector-origin-v1` и статус `artifact-declaration`: библиотека не удостоверяет
подлинность истории. Текущие PNG проверяются по странице, порядковому номеру,
bbox и digest; xref измеряется заново после оптимизации. Повреждённая или
устаревшая связь даёт `pdf.mapping-history-invalid`/`pdf.mapping-history-stale`
в диагностике импорта; соответствующая история не присоединяется к изображению.
Данные не исполняются, адреса исходных файлов не открываются.

```python
from opendoc_formats import read_pdf_origin_mapping

mapping = read_pdf_origin_mapping("output.pdf")
```

Карта импорта имеет профиль `pdf-imported-vector-origin-v1`, `staged` и SHA-256
текущего файла; `assessment_complete` относится только к проверенным связям.
Текущие resource IDs принадлежат свежей модели импорта. Редактируемая модель
переносит только декларацию происхождения в свойствах изображения; старые
model/resource/native handles в неё не записываются. Удаление изображения
удаляет связь из следующего PDF. `VISUAL` означает недоступную исходную
векторную семантику и не утверждает новую потерю пикселей PNG при каждом цикле.
Аутентификация происхождения не заявляется. [Композиция карт](object-mapping.md)
поддерживает явно объявленные bridge relations и группы split/merge.

### Автоматическая замена SVG

PNG создаётся существующим PyMuPDF-движком с ограничением до 16 млн пикселей
и 8192 по стороне. Это визуальная замена, а не редактируемая векторная структура.
В карте `pdf.svg-rasterized`/`svg-rasterization`, `VISUAL` и LOSS обозначают эту границу.
Для такого PNG replacement имеет scope `target` и указывает на raster resource
свежего нативного импорта итогового PDF; исходный SVG resource ID остаётся в source.

Изображения без Box сохраняют обычную Story-верстку. Внутренние временные
растры позволяют связать каждое вхождение с конкретной нативной вставкой;
они заменяются исходным PNG до сохранения. Размеры, прозрачность и смешанный
текст проверены сравнением итоговых пикселей с PNG-путём. При неподтверждённой
связи `pdf.svg-target-unconfirmed` даёт адресный ERROR, экспорт сохраняет
предыдущий файл. Повтор одного SVG в колонтитулах имеет несколько measured targets.
Служебная белая HTML-подложка заменена прозрачной: на обычной PDF-странице
это сохраняет вид и не создаёт отдельную неприменимую группу векторов.

История сохраняется через два PDF/JSON цикла, перестановку и удаление.
Отказ качества/публикации удаляет target replacement и actual target claims.
Все ограничения SVG-растеризации движка и сложности PDF paint order остаются
явными; карта не доказывает поддержку всей спецификации SVG.
